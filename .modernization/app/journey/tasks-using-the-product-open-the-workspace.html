Get back to the policy work where it

Get back to the policy work where it was left: the last policy sources and policy definitions are ready to browse.

4 steps today → 6 proposed34 rules kept · 0 droppedUsing the productProposed

Today, read from the codeModernized: Resume where I left off

1Start working with the same sources as last time

Reads the remembered preferences (carrying on with defaults if they cannot be kept), uses the local policy files for both user and computer on a first start, and if the saved sources cannot be opened tells the person and falls back to the local policy files.

2Have the policy definitions available

Loads the remembered definitions folder, or the Windows default one. If problems are found asks whether to keep the partly loaded set; if loading fails offers to use the default folder, or says the definitions could not be loaded and leaves the workspace empty.

3Know whether changes can be kept

Names each source, checks if it can be written, loads its comments if it has a comment location, and warns when a source is not fully writable.

4Start browsing policies

Shows the categories for both user and computer policies.

keptHave my preferences remembered

Preferences are the base for everything that follows and keep their quiet fallback.

mergedGet back to the policy sources I used last

Choosing, opening and checking the sources is one outcome, so it is one step with no questions.

keptGet the policy definitions I last used

Definitions decide what can be browsed, so they are loaded before anything is shown.

splitHave my policy comments alongside

Comments are separate from the sources and their failure no longer hides inside the sources step.

mergedKnow whether the workspace is ready to change

One summary replaces separate notices per source.

keptBrowse everything

Starting on the broadest view means nothing is hidden at first.

Why this way recommended

Everything the person last worked with is brought back in the order they care about, and anything wrong is reported once, in one place.

Keeps every rule, removes the scattered notices by reporting the state of the workspace once, and is the simplest to explain: what you left is what you get.

Trade-off: The person waits for all sources and the definitions to be ready before the first view appears.

The architecture, modernized

Rules kept and dropped: 34 kept, 0 dropped
  • When the program's settings area in the registry cannot be opened or created, the program carries on without it: settings read as their defaults, changes are dropped, and the person is not told, so settings are not remembered between runs.
  • The program allows secure connections using TLS 1.0, 1.1 and 1.2 only, so downloads use no other protocol.
  • On first start, when no policy sources were saved, both the user source and the computer source open as the local Group Policy files (Local GPO) with no extra location.
  • When the previously saved policy sources cannot be opened, the person is told "The previous policy sources are not accessible.
  • Opening new policy sources first closes the ones already open.
  • When the policy sources dialog opens with the last-used sources, each side is set to the remembered kind (Local GPO, Registry, POL file, Scratch space, and for users also per-user GPO or user hive), and the registry path, file name, SID or hive path is filled in only for the kinds that carry one.
  • A source read through the file branch covers a POL file, the local Group Policy and a per-user Group Policy, each with a Registry.pol path.
  • When the Registry.pol of a POL file source, the local Group Policy or a per-user Group Policy does not exist, it is created empty with its folder and treated as writable; a mistyped SID therefore creates a new folder and empty file under the per-user policy folder.
  • A user hive source is mounted by loading the hive file under a fresh temporary name in the machine registry, after the backup and restore privileges are switched on.
  • A registry source must start with HKCU, HKEY_CURRENT_USER, HKU, HKEY_USERS, HKLM or HKEY_LOCAL_MACHINE (any case); otherwise it is refused with "The root key is not valid." A path after the root is opened, and created if missing.
  • The path of a policy source is fixed by its kind: Local GPO uses the Registry.pol file of the system's local Group Policy (user or machine folder) and its gpt.ini; a per-user GPO uses the folder named by the person's SID under GroupPolicyUsers; a POL file and a user hive use the path given; Scratch space has none.
  • A Scratch space source is an empty policy store that can be changed but is never saved anywhere.
  • A source is writable by default for Scratch space; for a registry source it is 'no writing' when the write test failed; for others it is 'no commit' when the file or hive could not be opened for writing.
  • A registry source counts as writable only when a test value can be written under Software\Policies and removed again; otherwise it is read-only.
  • The source name shown in the status bar is Local GPO, Registry, File, User GPO, User hive or Scratch space, followed by the path or SID in brackets when there is one.
  • A policy file is refused when its format version is not 1, with the message 'Unknown (newer) version of POL format'.
  • A policy file is refused when it does not start with the 'PReg' signature, with the message 'Missing PReg signature'.
  • When a policy file is read and the same key and value name occur twice, the later entry wins.
  • When a policy file is read, an extra empty character after the value name, as Microsoft's documentation allows, is skipped.
  • When a policy file is saved, entries are written in alphabetical order, so a key-clearing marker is always written before the values it clears.
  • When a number is saved to the live registry, an unsigned 32-bit or 64-bit number is converted to the signed number the registry stores with the same bits, and the key is created if missing.
  • When a value is deleted in the live registry and its key does not exist, nothing happens. A missing value is not an error.
  • The definitions folder to load is the one saved last time; when none is saved it is the Windows PolicyDefinitions folder.
  • When loading the saved definitions reports problems, the person is asked whether to keep using the workspace.
  • When the person chooses to load the default location, the workspace is replaced by an empty one and the Windows default folder is loaded into it.
  • When the Windows default folder itself fails to load, or fails to load after the person chose Yes, the person is told "Policy definitions could not be loaded: <reason>" and the workspace stays empty.
  • When the saved folder is not the Windows default and fails to load, the person is told "Policy definitions could not be loaded from "<folder>": <reason> Load from the default location?".
  • The comment file for a source sits beside its file: the POL file or hive path with the extension changed to .cmtx; for Local GPO or per-user GPO a file named comment.cmtx in the same folder; for the registry a file under the person's local application data folder (one for user, one for machine); Scratch space has none, so comments are unavailable.
  • A source's comments are used only when it has a comment file location.
  • No comment of a comment file can be read when any comment's policy reference has no colon or a prefix that is not declared, its text is not written as "$(resource.<id>)", its text id is missing, or two comments resolve to the same policy.
  • A comment file is refused as unreadable when it has no comment-definitions section, a namespace entry without a prefix, a comment without a policy reference, a text without an id, or a repeated prefix, policy reference or text id.
  • A policy source's writability is described as "is fully writable", "cannot be saved" (changes work in memory only) or "cannot be modified"; anything but fully writable counts as a problem.
  • After opening, if either source is not fully writable the person is told "Not all policy sources are fully writable." with the state of the user and the computer source; if both are fully writable, "Both the user and computer policy sources are loaded and writable." appears only when opening was not quiet (never at start).
  • The list of areas starts on "User or Computer", the first choice, so both user and computer policies are shown at start.
Data it touches: Policy definition set, Policy comment, Program preference
  • Policy definition set Owned by Policy Definitions. Identified by namespace, item name.
  • Policy comment Owned by Policy Source. Identified by policy name, area.
  • Program preference Owned by Workspace. Identified by preference name.
