Find the policies

Find the policies that control a given system setting, named by its key or value.

Today, read from the codeModernized: One line, split for me

1Give the registry key and value to look for.

Refuses when both are empty or the key begins with a root key, then builds a case-insensitive test matching policies with a registry value that meets every term, with key and value wildcards or prefixes interpreted.

2Start the search or abandon it.

Starts a search with the entered terms or closes without searching.

inferredGive whatever is known about the setting in one go, such as a path copied from documentation, a key, or a value name.Inferred

Removes the need to know in advance which box a piece of text belongs to.

reorderedSee at once whether the terms can be used.

Feedback comes while typing, not after pressing search.

mergedGet the policies that control the setting.

The search runs from the entry itself, with no separate request step.

Why this way recommended

The person pastes or types whatever they have in one line, such as a full setting path ending in a value name, and the system works out which part is the key and which the value, checking as they go.

Fewest steps and least to know: one entry, the system infers the split and shows how it read it, while every matching and refusal rule is kept.

Trade-off: The system may guess the split wrongly for ambiguous text, so it must show how it read the text.

The architecture, modernized

Rules kept and dropped: 8 kept, 0 dropped
  • Find by registry starts a search with what the person entered.
  • When Search is pressed with both the key and the value empty, the search is refused and the person is told "Please enter search terms."
  • When the key text starts with HKLM\, HKCU\, HKEY_LOCAL_MACHINE\ or HKEY_CURRENT_USER\, the search is refused with "Policies' root keys are determined only by their section.
  • A value-name term must match the whole value name; "*" and "?" act as wildcards, so without them the name must be equal.
  • A key term containing a backslash but no wildcard matches policies whose key path starts with that text.
  • A key term containing "*" or "?" must match the whole key path as a wildcard pattern.
  • A policy matches a registry search when at least one registry value it reads or writes meets every term entered; matching ignores case.
  • A key term with no backslash and no wildcard matches policies having a key path with a part equal to that text.
Dropped: 1 action
  • Closes the dialog as cancelled when Escape is pressed There is no separate request to cancel; clearing the entry abandons the search.
Data it touches: Policy setting

Other ways considered: 2
  • Describe the setting 4 steps. The person states the key, the value, or both, is told at once if the terms cannot be used, and gets the matching policies. Trade-off: Still asks the person to know whether the text they have is a key or a value name.
  • Guided lookup 5 steps. For people who rarely search by setting, a short prompted path asks what they know, explains the forms a key or value may take, and then searches. Trade-off: More steps than the other variants, so slower for people who search often.
