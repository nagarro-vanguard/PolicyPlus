Save the policy settings and comments

Save the policy settings and comments to their sources, make them take effect where possible, and remember the chosen sources for next time.

4 steps today → 2 proposed31 rules kept · 0 droppedChoosing and saving policy sourcesProposed

Today, read from the codeModernized: Save in one go

1Keep the comments written on policies.

Writes each source's comments, with generated text identifiers, replacing the earlier content of the comment file; sources without comment support are skipped.

2Keep the policy settings in each source.

Writes a source only if fully writable, otherwise reports it as not writable; stores values, deletions, clearances and forgotten values in the source's own form, with its numbers, texts and lists encoded.

3Have the saved settings take effect.

Depending on the kind of source, raises the policy version record and asks Windows to refresh, applies the difference to the running account's registry, or reports that it was already applied, will apply on closing, or was discarded.

4Know the outcome and find the same sources next time.

Remembers the chosen source kinds and locations, and tells the person Success with the user and computer outcomes, or that saving failed and why.

keptSave my changes

One request, no sub-decisions: the system works out how each source takes effect.

inferredKnow the outcome of each source

The outcome per source tells the person what is live without asking.

Why this way recommended

The person asks once to save and the system does everything, then reports each source's outcome.

One request does the whole job with the outcome per source told afterwards, keeping every ordering and per-source rule.

Trade-off: The person has no chance to review before the system writes.

The architecture, modernized

Rules kept and dropped: 31 kept, 0 dropped
  • When comments are saved, each comment gets its own text id built from the policy's namespace, policy name and a running number, and each distinct namespace gets a prefix made from its name (dots turned into underscores) and the running number.
  • Saving comments writes every comment and text held in memory into the target file, in schema version 1.0, replacing what the file held before.
  • A source's comment list is saved to its comment file location whenever the list exists, even when empty; a source without comment support has no list and is skipped.
  • A multiple-string value is stored as its strings each followed by an empty character, with one more empty character closing the list.
  • A 64-bit number is stored in a policy file as 8 bytes, lowest byte first.
  • A 32-bit number is stored in a policy file as 4 bytes, lowest byte first.
  • Text stored in a policy file is written in two-byte characters followed by a closing empty character.
  • A value written to a policy file is stored as text, expandable text, a 32-bit or 64-bit number or a multiple string by its stated type.
  • When a value is set in a policy file, it replaces any value already held under that name.
  • When a value is marked for deletion in a policy file, any value or marker already held under that name is dropped first.
  • When a value is forgotten in a policy file, both the value and its deletion marker are removed, so the policy reverts to not saying anything about it.
  • When a policy file is clearing a key, all values and markers under the key are dropped and a single clear-all marker is stored.
  • When a policy file's changes are applied to another source, an entry is saved only if it has a non-empty value name that does not start with '**'.
  • When a policy file's changes are applied to another source, an entry starting '**deletekeys' clears each key named in its semicolon-separated list under the entry's key, using lower-case names.
  • When a policy file's changes are applied to another source, an entry named '**deletevalues' deletes each value in its semicolon-separated list, using lower-case names.
  • When a policy file's changes are applied to another source, an entry named '**del.' plus a value name deletes that value, using the lower-case key and value names.
  • When a policy file's changes are applied to another source, an entry starting '**delvals' clears the whole key, using the lower-case key name.
  • When a newer policy file is applied over an older one, values the old file held and the new one dropped are forgotten in the target, but only if they sit under the three policy branches of the registry.
  • A REG file cannot be used as a source for forgetting a value: the request fails with 'not implemented'.
  • When a value is saved into a REG file, it is ignored if a source branch is set and its key lies outside that branch.
  • When a value is deleted in a REG file, the request is ignored if a source branch is set and the key lies outside it, or if the key is already marked for removal.
  • When a key is cleared in a REG file, the request is ignored if a source branch is set and the key lies outside it.
  • In the live registry, 'forgetting' a value deletes it, because the registry cannot remember a pending deletion.
  • Clearing a key in the live registry deletes every value in it but leaves the key and its subkeys. Forgetting a key's clearance does nothing.
  • When gpt.ini does not exist, a new one is written with the General section, both extension-name lines and Version 65537.
  • When gpt.ini is updated and already exists, its Version number is raised by 1 for a machine source and by 65536 for a user source; if no Version line exists, it is set to 65537 (both parts at 1).
  • When gpt.ini is updated, the Machine and User extension-name lines for the registry policy are added if missing and left untouched if present.
  • Saving writes each source's comments first, then writes a source only if it is fully writable (otherwise reported as "not writable"), then remembers the chosen source types and locations for the next start.
  • Saving a POL file source writes the file only ("saved to disk"); a registry source reports "already applied" because it was changed live; a user hive reports "will apply when policy source is closed"; Scratch space reports "discarded".
  • Saving a local Group Policy source writes the Registry.pol file, raises the gpt.ini version, and then, on Windows editions that list as having Group Policy (decided by a fixed list of product edition codes), asks Windows to refresh policy ("saved to disk and invoked policy refresh").
  • Saving a per-user GPO writes its Registry.pol file, raises its gpt.ini version and asks Windows to refresh user policy ("saved to disk and invoked policy refresh").
Data it touches: Policy comment, Policy setting, Program preference
  • Policy comment Owned by Policy Source. Identified by policy name, area.
  • Policy setting Owned by Policy State. Identified by policy name, area.
  • Program preference Owned by Workspace. Identified by preference name.
Other ways considered: 2
  • Check first, then save 3 steps. The system first checks that every source can be written and says what will happen, then saves on the person's go-ahead. Trade-off: Two stages even when all is well.
  • Review, then save 6 steps. The person sees what will be saved and to which sources, saves, and then reads the outcome of each source. Trade-off: One extra look before saving for people who just want to save.
