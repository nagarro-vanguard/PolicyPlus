Add a new key, or a new value of a chosen kind, to a policy file.

Done by person. Today's way, against the ways we propose.

How it is done today

Worked out from the code, so each step says how sure we are. Marks are yours: what hurts, what is never used, what is wrong.

1. Name a new key

Asks for the key name, checks it is valid and not taken under the same parent, and adds it as an empty key, selected in the list.

Stated by the code

2. Add a value to the selected key

Asks for the value name and one of five kinds, then asks for the data and stores it, replacing a value of the same name without warning.

Stated by the code

Ways we propose

Name, then kind, then data

task first

Adding a key is one name; adding a value is a name, a kind, then its data, each asked in turn.

Costs: Several small questions for a value, and a name error appears only after confirming.

kept 1. Give the new key a name

Asks for a name, ready to type; an empty name or backing out adds nothing.

takes the place of today's 1

Why, and what it keeps

Naming is all a key needs.

  • Adding a key does nothing when the name is left empty or the dialog is cancelled; otherwise the key is created under the selected key, or at the top level when nothing is selected, as an empty key, and is selected in the list.
  • When the key name dialog is confirmed, the typed name is returned unchecked; when it is cancelled, an empty name is returned, so an empty typed name and a cancel look the same to the caller.

kept 2. Have the key created in the right place

Refuses a name with a backslash or one already used under the same parent, ignoring case; otherwise adds the empty key under the selected key, or at the top, and selects it.

takes the place of today's 1

Why, and what it keeps

The refusals keep the file consistent.

  • A new key name is refused with "The key name is already taken." when a key of that name, ignoring case, already exists under the same parent.
  • A new key name is refused with "The key name is not valid." when it contains a backslash.
  • Adding a key does nothing when the name is left empty or the dialog is cancelled; otherwise the key is created under the selected key, or at the top level when nothing is selected, as an empty key, and is selected in the list.

kept 3. Name the new value and choose its kind

Offers string, expandable string, list of strings, 32-bit and 64-bit number, starting on string; backing out adds nothing.

takes the place of today's 2

Why, and what it keeps

The kind decides what data can be entered.

  • The new registry value dialog offers the types String, Expandable string, List of strings, 32-bit DWord and 64-bit QWord, and starts on String. Confirming returns the typed name, unchecked and possibly empty, with the chosen type; cancelling returns neither.

kept 4. Enter the value's data

Starts from empty text, zero or an empty list by kind; numbers stay within the limits of their size; the value is stored under the selected key only on confirming, replacing a value of the same name without warning.

takes the place of today's 2

Why, and what it keeps

Data entry belongs with the value.

  • Adding a value to the selected key lets the person choose a name and one of five kinds; the starting data is empty text, zero, or an empty list by kind, and the value is stored only if the person then confirms its data. A value of the same name in that key is replaced without warning.
  • A number entered for a registry value is limited to 0 to 4,294,967,295 for a 32-bit value and to 0 to 18,446,744,073,709,551,615 for a 64-bit value.
  • Editing a value offers a text, number or list-of-text dialog by kind: text kinds (plain and expandable) a text box, 32-bit and 64-bit numbers a number box, lists of text a multi-line box. Any other kind, such as binary, is refused with "This value kind is not supported." and nothing changes. Cancelling the dialog leaves the value as it was.
