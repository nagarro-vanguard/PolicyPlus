Save the policy settings and comments to their sources, make them take effect where possible, and remember the chosen sources for next time.

Done by person. Today's way, against the ways we propose.

How tasks are done today confirmed 2026-11-18
How tasks should be done confirmed 2026-11-18

How it is done today

Worked out from the code, so each step says how sure we are. Marks are yours: what hurts, what is never used, what is wrong.

1. Keep the comments written on policies.

Writes each source's comments, with generated text identifiers, replacing the earlier content of the comment file; sources without comment support are skipped.

Stated by the code

2. Keep the policy settings in each source.

Writes a source only if fully writable, otherwise reports it as not writable; stores values, deletions, clearances and forgotten values in the source's own form, with its numbers, texts and lists encoded.

Stated by the code

3. Have the saved settings take effect.

Depending on the kind of source, raises the policy version record and asks Windows to refresh, applies the difference to the running account's registry, or reports that it was already applied, will apply on closing, or was discarded.

Stated by the code

4. Know the outcome and find the same sources next time.

Remembers the chosen source kinds and locations, and tells the person Success with the user and computer outcomes, or that saving failed and why.

Stated by the code

split 2. Save the comments

The system writes each source's comments first, with generated ids and in the fixed comment format, replacing earlier content; sources without comments are skipped.

takes the place of today's 1, 2, 3, 4

Why, and what it keeps

Comments are their own stage so a problem there is visible apart from settings.

  • When comments are saved, each comment gets its own text id built from the policy's namespace, policy name and a running number, and each distinct namespace gets a prefix made from its name (dots turned into underscores) and the running number.
  • Saving comments writes every comment and text held in memory into the target file, in schema version 1.0, replacing what the file held before.
  • A source's comment list is saved to its comment file location whenever the list exists, even when empty; a source without comment support has no list and is skipped.
  • Saving writes each source's comments first, then writes a source only if it is fully writable (otherwise reported as "not writable"), then remembers the chosen source types and locations for the next start. The person sees "Success." with the user and computer outcomes, or "Saving failed!" with the reason.

split 3. Save the settings to each source

The system writes a source only if fully writable, reporting otherwise that it is not writable, storing values in the policy file encoding and updating the source in the way its kind needs.

takes the place of today's 1, 2, 3, 4

Why, and what it keeps

Each source kind is handled by one rule set, hidden from the person.

  • A multiple-string value is stored as its strings each followed by an empty character, with one more empty character closing the list.
  • A 64-bit number is stored in a policy file as 8 bytes, lowest byte first.
  • A 32-bit number is stored in a policy file as 4 bytes, lowest byte first.
  • Text stored in a policy file is written in two-byte characters followed by a closing empty character.
  • A value written to a policy file is stored as text, expandable text, a 32-bit or 64-bit number or a multiple string by its stated type. Every other type is stored as raw bytes with that type.
  • When a value is set in a policy file, it replaces any value already held under that name. A deletion marker for the name is not removed.
  • When a value is marked for deletion in a policy file, any value or marker already held under that name is dropped first. A deletion marker holding the number 32, as Microsoft does, is added unless the value is already marked or its key is cleared.
  • When a value is forgotten in a policy file, both the value and its deletion marker are removed, so the policy reverts to not saying anything about it.
  • When a policy file is clearing a key, all values and markers under the key are dropped and a single clear-all marker is stored.
  • When a policy file's changes are applied to another source, an entry is saved only if it has a non-empty value name that does not start with '**'. Other marker-style entries and entries with an empty value name are skipped without notice. A saved value keeps its original letter case and type.
  • When a policy file's changes are applied to another source, an entry starting '**deletekeys' clears each key named in its semicolon-separated list under the entry's key, using lower-case names. Clearing removes only that key's own values, not its subkeys.
  • When a policy file's changes are applied to another source, an entry named '**deletevalues' deletes each value in its semicolon-separated list, using lower-case names.
  • When a policy file's changes are applied to another source, an entry named '**del.' plus a value name deletes that value, using the lower-case key and value names.
  • When a policy file's changes are applied to another source, an entry starting '**delvals' clears the whole key, using the lower-case key name. Entries are applied in sorted order, so clear-all entries come before values. Clearing a live registry key removes only that key's own values.
  • When a newer policy file is applied over an older one, values the old file held and the new one dropped are forgotten in the target, but only if they sit under the three policy branches of the registry.
  • A REG file cannot be used as a source for forgetting a value: the request fails with 'not implemented'. Applying a newer policy file over an older one to a REG file fails this way for any dropped value under a policy branch.
  • When a value is saved into a REG file, it is ignored if a source branch is set and its key lies outside that branch. When no branch is set, every key is accepted. Any value already stored under that name is replaced.
  • When a value is deleted in a REG file, the request is ignored if a source branch is set and the key lies outside it, or if the key is already marked for removal. When no branch is set, every key is accepted. Otherwise the value is recorded as deleted.
  • When a key is cleared in a REG file, the request is ignored if a source branch is set and the key lies outside it. When no branch is set, every key is accepted. Otherwise the key's earlier entries are replaced by a key-removal entry.
  • In the live registry, 'forgetting' a value deletes it, because the registry cannot remember a pending deletion.
  • Clearing a key in the live registry deletes every value in it but leaves the key and its subkeys. Forgetting a key's clearance does nothing.
  • When gpt.ini does not exist, a new one is written with the General section, both extension-name lines and Version 65537.
  • When gpt.ini is updated and already exists, its Version number is raised by 1 for a machine source and by 65536 for a user source; if no Version line exists, it is set to 65537 (both parts at 1).
  • When gpt.ini is updated, the Machine and User extension-name lines for the registry policy are added if missing and left untouched if present.
  • Saving writes each source's comments first, then writes a source only if it is fully writable (otherwise reported as "not writable"), then remembers the chosen source types and locations for the next start. The person sees "Success." with the user and computer outcomes, or "Saving failed!" with the reason.

split 4. Have the changes take effect where possible

The system refreshes policy for local and per-user group policy sources, applies the difference to the running account where the edition has no group policy, and notes what will apply later or was discarded.

takes the place of today's 1, 2, 3, 4

Why, and what it keeps

Taking effect is stated as its own outcome.

  • Saving a local Group Policy source writes the Registry.pol file, raises the gpt.ini version, and then, on Windows editions that list as having Group Policy (decided by a fixed list of product edition codes), asks Windows to refresh policy ("saved to disk and invoked policy refresh"). On other editions, the difference between the file as last on disk (read at the moment of saving) and the new content is applied to the running account's own registry (the current user's for a user source, the machine's for a machine source) and all windows are notified ("saved to disk and applied diff to Registry").
  • Saving a per-user GPO writes its Registry.pol file, raises its gpt.ini version and asks Windows to refresh user policy ("saved to disk and invoked policy refresh").
  • Saving a POL file source writes the file only ("saved to disk"); a registry source reports "already applied" because it was changed live; a user hive reports "will apply when policy source is closed"; Scratch space reports "discarded".
