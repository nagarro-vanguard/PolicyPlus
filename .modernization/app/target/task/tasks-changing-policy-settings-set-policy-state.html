merged 1. Choose the policy's scope and see what it is

The system shows the policy's name, help and support text, the side it applies to (computer or user, fixed when the policy has one only), whether that side can be changed, and the state it is in today.

Why, and what it keeps

One step shows the policy and its scope and reloads the state when the side changes, instead of two separate moments.

  • A policy that applies to both computer and user can be edited for either, starting on Computer when no section was given; a policy for one section is fixed to that section and the section choice is unavailable.
  • Choosing Computer or User in the dialog switches the source, its writability and its comments to that section, and reloads the chosen state (Enabled, Disabled or Not Configured) from it. Option values are replaced only for options the section stores when it is Enabled; other values typed earlier stay in the controls.
  • OK and Apply are available only when the chosen policy source can be written to.
  • The Supported on box shows the supported-on name of the policy and is empty when the policy names none.
  • The state shown when the dialog opens follows the policy's present state in the source being edited: Enabled, Disabled, or Not Configured for anything else, including an unclear state.
  • The comment box is disabled and reads "Comments unavailable for this policy source" when the source has no comments; otherwise it shows the policy's stored comment, or is empty when there is none.
  • Option controls can be edited only while Enabled is chosen; with Disabled or Not Configured they are greyed out.

Options become editable only when on is chosen; the other two states need nothing more.

Why, and what it keeps

The state decision comes first so the person is asked for options only when they matter.

  • Option controls can be edited only while Enabled is chosen; with Disabled or Not Configured they are greyed out.

defaulted 3. Fill in the options

Each option shows the value stored today or its default, within its limits; numbers outside limits are brought back to the limit, text is capped, choices are sorted as the definition says.

takes the place of today's 4

Why, and what it keeps

Options start from what is stored so the person changes only what they want to change.

  • When the policy is Enabled, each option control is set to the value found in the source: numbers into number boxes, text into text and combo boxes, the matching item in drop-downs, true or false into check boxes, lines into multi-line boxes and the stored list into the list editor.
  • A choice element is read as the position of the first item whose own value is present and, when the item has a value list, whose list is wholly present; when no item matches, the position is -1.
  • A list element whose entries have names the person provides is read as every stored name with its value, under the element's key.
  • A list of values counts as present only when every value in it is present.
  • The saved value of a multi-line text element is read as stored, without first checking that it exists.
  • A check box starts with the presentation's default state.
  • A checkbox is on when its on value (or all values of its on list) is present, or, with neither defined, when its value is 1; it is off in every other case, including when its off value is present.
  • A list element whose entry names do not matter is read as a list of values: when the list has a prefix, the stored values named prefix1, prefix2, and so on, in order, until the first number that is missing; otherwise every stored value name under the key.
  • The saved value of a number or text element is read as stored; the reading assumes the value exists and is of the right kind, and is not checked first. A checkbox is read by its own rule.
  • A plain text entry is limited to the maximum length the policy defines and starts with the presentation's default text.
  • A number entered with a spin box is limited to the minimum and maximum the policy defines, in steps the presentation sets, and starts at the presentation's default.
  • A drop-down list shows the policy's choices by their translated names, sorted unless the presentation turns sorting off, and preselects the default choice when the presentation names one; otherwise nothing is selected.
  • A text entry with suggestions is limited to the maximum length the policy defines, starts with the presentation's default text, and lists the presentation's suggestions, sorted unless the presentation turns sorting off.
  • Keys other than digits and control keys are ignored in a numeric text box.
  • A plain number box keeps any text a whole-number reading accepts, including a leading sign or spaces; other text is replaced by the default. A number above the maximum or below the minimum is replaced by that limit. Numbers above 2,147,483,647 are replaced by the default even when the policy maximum is higher. Only typing is restricted to digits; pasted text is not. A negative number kept where the minimum is below zero is converted to an unsigned number when applied.

merged 4. Edit list entries where an option is a list

The person adds, removes and names entries; the system refuses two entries with the same name and ignores the empty spare row.

takes the place of today's 4

Why, and what it keeps

Entering and collecting list entries is one piece of work, not an editor opened and closed.

  • When the list editor is confirmed for a list where the person names each entry, and two entries have exactly the same name, it is refused with "Multiple entries are named "<name>"! Remove or rename all but one." and nothing is returned. Names are compared exactly, so Run and run are accepted as two entries. A name cell never filled in stops the dialog with an unhandled error.
  • When the list editor is confirmed for a list without names, every row except the empty new row at the bottom is returned in the order shown, with no check that a cell has content; a row whose value cell was never filled is returned as an empty entry. For named lists the same new row is ignored.

split 5. Add a comment on why

Where the source keeps comments the person can record a reason; where it does not, the system says comments are unavailable.

takes the place of today's 1, 5

Why, and what it keeps

The reason for a change is asked for as its own small step, not hidden among options.

  • The comment box is disabled and reads "Comments unavailable for this policy source" when the source has no comments; otherwise it shows the policy's stored comment, or is empty when there is none.

merged 6. Save and either carry on or finish

The system forgets what the policy held, writes the chosen state, options and comment, and then keeps the person on the policy or leaves it, reporting a change if anything was saved earlier.

takes the place of today's 6

Why, and what it keeps

Saving, saving and leaving, and reporting the outcome are one decision.

  • When a policy is set to Disabled and the definition gives no off value, its registry value is removed. A defined off value, with any extra off values, is saved instead.
  • When a policy is set to Enabled and the policy has a registry value name but defines no explicit on value, the value is saved as the number 1.
  • When a number setting is saved, it is written as text if the definition says to store it as text, otherwise as a 32-bit number.
  • When a policy is applied and the source supports comments, an empty comment box removes the policy's stored comment and any text replaces or adds it.
  • When a list setting is saved, entries that carry their own names are saved under those names. Otherwise each entry is numbered from 1, named with the definition's prefix plus its number, or named after its own text when the definition has no prefix.
  • A setting that names its own registry key is saved under that key. Otherwise it is saved under the policy's key.
  • When a multi-line text setting is saved, it is written as a multiple-string value.
  • When a policy is set to Disabled, each setting gets only its own removal. A list setting has all values under its key removed, even when its definition says to keep other entries. A checkbox with a defined off value or off list gets those saved, and every other setting has its single value removed. Extra values listed for a chosen item, a checkbox's on list and the policy's own on list are left in place.
  • When Enabled is chosen, applying writes every option of the policy whatever its value, including options never filled in.
  • When a text setting is saved, it is written as an expandable text string if the definition says so, otherwise as a plain text string.
  • When a policy is set to Enabled, its own on value is saved and any extra values listed for the on state are saved with it. A key left blank in a list falls back to the policy's key.
  • When a checkbox setting is saved, a ticked box with no defined on value first saves the number 1, and an unticked box with no defined off value first removes the value. The defined on or off value is then saved, with the extra values listed for that state, and overwrites the first step.
  • When a list setting is saved and the definition does not say to keep other entries, every existing value under the list's key is removed first. A list with no supplied entries then stays empty.
  • When a registry value is written for a policy, a value defined as 'delete' is removed, a numeric value is saved as a 32-bit number and a text value as a text string. A policy with no value defined writes nothing.
  • Applying a policy first forgets everything the source holds for it; Enabled then writes every option's current value, Disabled writes the disabled state, and Not Configured leaves the policy with no values.
  • When a policy is set to Not configured or Unknown, SetPolicyState writes and removes nothing. Callers forget the policy's old values first, so Not configured works by that removal alone.
  • When a policy is set to Enabled, only the settings the person supplied are written. A setting with no supplied value is left as it was.
  • The registry values a policy touches are its own value, those in its value lists, those of its elements (the whole key for list elements) and those of checkbox and choice sub-lists, each counted once.
  • When a policy is forgotten, the whole key of each of its list elements is cleared and every registry value it touches is dropped from the source, so it reads as Not configured.
  • When a key's clearance is forgotten in a REG file, the key-removal entry is dropped if it exists. The request is ignored if a source branch is set and the key lies outside it. When no branch is set, every key is accepted.
  • When a key's clearance is forgotten in a policy file, every clear-all marker for that key is removed.
  • When the policy setting dialog is closed by any other means, it is still reported as a change if Apply was used earlier.
  • OK writes the policy to the source and closes the dialog as a change.
  • Apply writes the policy to the source, keeps the dialog open and records that a change was made.
  • Closing the policy setting dialog with Cancel is reported as a change when Apply was used earlier in that session, and as a cancel otherwise.

      • When a policy is set to Disabled and the definition gives no off value, its registry value is removed. A defined off value, with any extra off values, is saved instead.
      • When a policy is set to Enabled and the policy has a registry value name but defines no explicit on value, the value is saved as the number 1.
      • When a number setting is saved, it is written as text if the definition says to store it as text, otherwise as a 32-bit number.
      • When a policy is applied and the source supports comments, an empty comment box removes the policy's stored comment and any text replaces or adds it.
      • When a list setting is saved, entries that carry their own names are saved under those names. Otherwise each entry is numbered from 1, named with the definition's prefix plus its number, or named after its own text when the definition has no prefix.
      • A setting that names its own registry key is saved under that key. Otherwise it is saved under the policy's key.
      • When a multi-line text setting is saved, it is written as a multiple-string value.
      • When a policy is set to Disabled, each setting gets only its own removal. A list setting has all values under its key removed, even when its definition says to keep other entries. A checkbox with a defined off value or off list gets those saved, and every other setting has its single value removed. Extra values listed for a chosen item, a checkbox's on list and the policy's own on list are left in place.
      • When Enabled is chosen, applying writes every option of the policy whatever its value, including options never filled in.
      • When a text setting is saved, it is written as an expandable text string if the definition says so, otherwise as a plain text string.
      • When a policy is set to Enabled, its own on value is saved and any extra values listed for the on state are saved with it. A key left blank in a list falls back to the policy's key.
      • When a checkbox setting is saved, a ticked box with no defined on value first saves the number 1, and an unticked box with no defined off value first removes the value. The defined on or off value is then saved, with the extra values listed for that state, and overwrites the first step.
      • When a list setting is saved and the definition does not say to keep other entries, every existing value under the list's key is removed first. A list with no supplied entries then stays empty.
      • When a registry value is written for a policy, a value defined as 'delete' is removed, a numeric value is saved as a 32-bit number and a text value as a text string. A policy with no value defined writes nothing.
      • Applying a policy first forgets everything the source holds for it; Enabled then writes every option's current value, Disabled writes the disabled state, and Not Configured leaves the policy with no values.
      • When a policy is set to Not configured or Unknown, SetPolicyState writes and removes nothing. Callers forget the policy's old values first, so Not configured works by that removal alone.
      • When a policy is set to Enabled, only the settings the person supplied are written. A setting with no supplied value is left as it was.
      • The registry values a policy touches are its own value, those in its value lists, those of its elements (the whole key for list elements) and those of checkbox and choice sub-lists, each counted once.
      • When a policy is forgotten, the whole key of each of its list elements is cleared and every registry value it touches is dropped from the source, so it reads as Not configured.
      • When a key's clearance is forgotten in a REG file, the key-removal entry is dropped if it exists. The request is ignored if a source branch is set and the key lies outside it. When no branch is set, every key is accepted.
      • When a key's clearance is forgotten in a policy file, every clear-all marker for that key is removed.
      • When the policy setting dialog is closed by any other means, it is still reported as a change if Apply was used earlier.
      • OK writes the policy to the source and closes the dialog as a change.
      • Apply writes the policy to the source, keeps the dialog open and records that a change was made.
      • Closing the policy setting dialog with Cancel is reported as a change when Apply was used earlier in that session, and as a cancel otherwise.
