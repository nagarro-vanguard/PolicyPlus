How it is done today

Worked out from the code, so each step says how sure we are. Marks are yours: what hurts, what is never used, what is wrong.

1. Say which identifier to look for and in which area.

Offers only the areas user or computer, user, and computer, and shows status symbols as the person types; the identifier is trimmed and looked up as a category, then a product, then a support definition, then a policy, showing what kind it found or that nothing matched.

Stated by the code

2. Confirm the identifier or give up.

Accepts whatever was typed, even when nothing matched, or abandons the request without a selection.

Stated by the code

3. See what was found.

Opens a visible category, opens a policy for editing and moves the list to it, shows the details of a product or support definition, or says the category is not visible or the object could not be found.

kept 1. Give the identifier of a category, product, support definition or policy.

Trims it and tries category, product, support definition then policy in that order, cutting a user or computer suffix first, and shows the kind found, nothing found, or nothing yet.

takes the place of today's 1

Why, and what it keeps

The person sees what the identifier means before leaving.

  • Text typed in Find by ID is trimmed and looked up in this order: category, product, support definition, then policy. The first kind that matches is selected, with its own icon shown; a policy is looked up only when no other kind matches.
  • A policy ID may end with "@U" to mean the user section or "@C" to mean the computer section; without a suffix, or with any other suffix, the policy applies to both sections. The suffix is cut off before the policy lookup, so an unknown suffix still finds the policy.
  • When the text matches nothing, nothing is selected and a "not found" icon is shown; when the text is empty a blank icon is shown instead. The section from an earlier match is not cleared when the text changes to a non-policy.
  • The area choice offers only "User or Computer", "User" and "Computer", with no free text.

kept 2. Go to what was found.

Opens a category if visible, else says it is not visible; opens a policy in the computer area in preference to user, within its visible category, and tells the person when it is hidden; shows a product or support definition with its details; says not found otherwise.

takes the place of today's 3

Why, and what it keeps

Going is a deliberate step.

  • After finding by identifier, a category opens if it is visible, otherwise the person is told "The category is not currently visible. Change the view settings and try again."; a policy opens in the editor and the list moves to it; a product or support definition opens its details; anything else gives "That object could not be found.".
  • Moving to a policy first shows its category, but only when that category is visible in the tree; otherwise nothing happens and the person is not told. The policy row is then selected only if the policy is listed there. A policy hidden by the area choice or the filter leaves the category shown with nothing selected and no message; find by text and by registry do not check this before opening the editor.
  • A policy found by identifier opens in the lower-numbered of the area shown and the area found (computer is lower than user, user lower than both), so Computer wins over User.
  • Only one item in the policy list can be selected at a time.
  • After the edit dialog is accepted, which changes the open policy source in memory only, the list is refreshed in place if the current category is still visible; otherwise the program moves up to the nearest visible category. Nothing is written to disk until Save Policies.
  • Each entry of a support definition is listed by the name of the nested support definition when it is one, otherwise by the name of the product, otherwise as "<missing: " followed by the product code the entry names. Minimum and maximum versions are listed only for product entries that name a version range; a missing bound is shown blank.
  • The product details window lists every child revision of a product with its version and name; a product with no children shows an empty list.
  • A product with a parent shows the parent name and enables the parent button; a product with no parent shows a blank parent and the button is disabled.
  • The product details window shows a version number for major and minor revisions only; for a top-level product the version is blank.
  • The product details window labels a product "Major revision", "Minor revision" or "Top-level product" from its type.
  • The support details window states how a support definition matches products: "Match all the referenced products", "Match any of the referenced products", or "Do not match products" when it has no matching logic.
What this way leaves out

Where the cursor starts and how a window is dismissed are control details; nothing changes unless the person goes to the thing.

  • Clears the placeholder space and focuses the ID box
  • Closes the dialog as cancelled when Escape is pressed

Confirming an identifier that matched nothing is replaced by telling the person it was not found; the hidden deduplicate entry could not be started and has nothing to carry.

  • Closes the dialog with the typed ID accepted
