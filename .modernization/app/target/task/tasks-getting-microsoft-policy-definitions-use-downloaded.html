merged 1. Say that the downloaded definitions should become the ones in use.

The system takes the downloaded folder and finds the template files in it, ignoring everything else.

takes the place of today's 1, 2

Why, and what it keeps

Choosing the folder and loading it become one request instead of a window followed by a load.

  • Only files directly in the chosen folder whose names end in .admx (in any letter case) are loaded as templates; subfolders and other files are ignored.
  • After a successful download of definitions, the workspace is emptied, the downloaded folder loaded and saved as the definitions folder, and the view rebuilt; with no new folder nothing changes.
  • Closing the workspace or replacing it with a new one discards all loaded definitions and the previous search results.
  • The language for definition text is the saved language code, or the computer's own language when none is saved.

split 2. Be sure each template comes with its text in my language.

The system picks the language text for each template, preferring the person's language, then the same language family, then English, and refuses a template with none or with a flawed text.

takes the place of today's 1, 2

Why, and what it keeps

Finding the language text is its own visible stage so a missing language is named rather than left to a vague failure.

  • The language file for a template is taken from the subfolder named exactly by the language code if it holds this template's file; else from the first subfolder whose name starts with the same language part (before the dash, compared with capital letters mattering) that holds this template's file; else from the en-US subfolder if it holds it. A folder lacking the file is skipped.
  • When no language file is found in any of those places, the template file is refused with "The corresponding ADML is missing" and none of its content is loaded.
  • When the chosen language file cannot be parsed as XML, the template is refused with "The ADML XML couldn't be parsed: <detail>"; any other read problem gives "The ADML is invalid: <detail>".
  • A language file's text table is read only from its first text table, and each text is kept under its id; when the same text id appears twice, the file is refused as invalid and its template file is not loaded.
  • A language file's screen layouts are read only from its first presentation table; when the same layout id appears twice, the file is refused as invalid and its template file is not loaded.
  • When a language file has no policy resources section, or its revision is missing or not a number, the file is refused as invalid and its template file is not loaded.

reordered 3. Be sure the templates are sound.

The system reads and validates every template beside the current definitions, skipping and listing the ones it refuses and stopping at once on a missing namespace.

takes the place of today's 1, 2

Why, and what it keeps

Checking comes before replacing, so a bad download cannot spoil what the person has.

  • When a template file cannot be parsed as XML, it is refused with the message "Couldn't load <path>: The ADMX XML couldn't be parsed: <detail>."; any other read problem is refused with "The ADMX is invalid: <detail>".
  • A template file is refused as invalid when any of these is missing or unreadable: the policy definitions section; a namespace entry's prefix or namespace; a superseded-ADM file name; a minimum revision (missing or not a number); a support rule's name or display name; a support reference or range without its reference, or a version bound that is not a whole number; a product's name, display name or version index; a category's name or display name; a category's parent entry or its reference when the category has content; a policy's name, display name, key or class; a policy's category or supported-on reference; a number value's value; a list item's value name; a choice item's display name; or an option's id.
  • When a template declares no target namespace, loading the folder stops at once with an error: the files after it are not read, nothing is built, and the person sees the error text (a start-up load also discards the workspace).
  • When a template file's namespace is already held by a template file loaded earlier, it is refused with "The <namespace> namespace is already owned by a different ADMX file", so the same file cannot be added twice.
  • The namespace of a template is the one listed as its target; each prefix a template declares must be unique, and a repeated prefix refuses the file as invalid.
  • A template's superseded-ADM file name and minimum language revision are read when present; a superseded entry without a file name, or a minimum revision that is missing or not a number, refuses the template as invalid.
  • A category's explanation is optional. A category with any content inside it (even a comment) must contain a parent entry with a reference; otherwise the template is refused as invalid.
  • Products form three levels: a product, its major versions and their minor versions; deeper levels are not read, and each version must carry a version index or the file is refused as invalid.
  • An item's unique name is its template's namespace, a colon and its own name, so equal names in different templates stay apart.
  • A reference containing a colon uses the namespace the template declared for its prefix; with an unknown prefix it is taken as already complete; a reference without a colon belongs to the template's own namespace.
  • An XML attribute that is absent gives nothing.
  • An XML attribute that is absent, or whose text is not valid for the type of the stated default, gives that default.
  • When a template file is refused with a reported failure (unparsable, invalid, namespace already owned, or no usable language file), it is skipped and the failure is listed; the other files in the folder still load and the structures are built from those that loaded.

inferred 4. Understand what the policies, categories and products mean.

The system works out the categories, products, support rules, policies, options and their layouts for entering values, with their names and descriptions in the language.

takes the place of today's 1, 2

Why, and what it keeps

Everything is worked out from the template once, ahead of use, rather than as the person browses.

  • A name or description written as "$(string.<id>)" shows the language file's text for that id; an unknown id shows the code itself; any other text is shown as written; an empty value stays empty.
  • A policy takes its category and its 'supported on' rule from the references in its own content, and has options only when it contains an options section.
  • A category whose parent is named is attached under that parent, found among items of this load or of files loaded earlier; when the parent is not found, the category has no parent but is still listed among the top-level categories.
  • A policy is listed under the category its reference names, found in this load or earlier ones; when that category is not found the policy is kept in the policy list but belongs to no category.
  • A policy shows the 'supported on' rule its reference names, found in this load or earlier ones; when none is found it has none.
  • A child product (major or minor version) is attached under its parent product, which must be defined in the same template file; only products without a parent are listed as top-level products.
  • A support rule is 'any of' when its first logic element is "or", 'all of' when it is "and", and blank otherwise; only that first logic element is read, each reference or range in it becomes an entry, and a range may carry a minimum and maximum version.
  • A policy option of any kind other than number, yes/no, text, list, choice or multi-line text is dropped without notice.
  • Only labels, number boxes, text boxes, check boxes, combo boxes, drop-down lists, list boxes and multi-line text boxes are kept in a screen layout; any other control in the language file is dropped without notice.
  • A control keeps the reference id the language file gives it, which ties it to the matching setting option in the template file; a control without one has no id.
  • A policy gets a settings screen layout only when the template names one, the name is written as "$(presentation.<id>)", and the language file holds a layout with that id; in every other case the policy has none.
  • The text of a policy description is tidied for display: leading and trailing spaces are removed from every line and blank space at the end of the text is dropped.
  • A policy applies to computers when its class is "Machine", to users when "User", and to both for any other class value.
  • A policy applies to an area when its definition declares that area; a policy declared for both applies to each.
  • A policy is a preference, not a managed policy, when it names a registry key outside the three policy locations: software\policies, software\microsoft\windows\currentversion\policies and system\currentcontrolset\policies.
  • A registry key counts as a policy key when it is one of the three policy branches (software\policies, software\microsoft\windows\currentversion\policies, system\currentcontrolset\policies) or lies below one, regardless of case.
  • A registry value in a template is a delete marker, a number or a text, decided by the first of those it contains; a value with none of them is treated as a delete marker.
  • An option's registry value name is taken from its own value name, except for a list option that has a value prefix attribute: the prefix is used and the own value name only when that prefix is empty. A list option counts as prefixed whenever the attribute is present, even if empty.
  • A list option replaces other entries of its key unless marked additive, stores plain text unless marked expandable, numbers entries automatically unless the template says the person names them, and counts as prefixed only when a value prefix is given.
  • A number box takes default value 1, shows its up-down spinner and steps by 1 unless the language file says otherwise; an unreadable attribute value falls back to the same defaults.
  • A number option accepts 0 to 4,294,967,295 unless the template sets other limits, overwrites existing values unless marked soft, and is stored as a number unless marked as text; unreadable attribute values fall back to these defaults.
  • A text option allows 255 characters, is optional, is stored as plain text and overwrites existing values unless the template says otherwise; unreadable attribute values fall back to these defaults.
  • A check box starts unticked unless the language file marks it ticked.
  • A drop-down list has a preselected item only when the language file names one; otherwise none is preselected.
  • A choice option is optional unless marked required. Each choice keeps whichever of a single registry value and a list of values it contains, both when both are present; a choice with neither is accepted and changes nothing.
  • Entries of a combo box or drop-down list are sorted unless the language file says not to sort them.
  • A yes/no option takes its registry effect for true and false from true and false values and lists.
  • A policy's switched-on and switched-off effects are read from its enabled and disabled values and lists; a list entry names a value and optionally its own key, falling back to the list's default key.
  • A support rule entry is linked to the product its reference names; when no such product exists it is linked to the support rule of that name; when neither exists it stays unlinked.

merged 5. Switch to the new definitions.

The system empties the workspace, adds the staged definitions to the available ones, and remembers the folder as the definitions folder; with no new folder nothing changes.

takes the place of today's 1, 2

Why, and what it keeps

Emptying, loading and remembering are one switch that either happens whole or not at all.

  • When both a template file and its language file load, the template's categories, products, support rules and policies are staged for the next build and the pair is recorded as loaded under the template's namespace.
  • When the structures are built, all new categories, products, support rules and policies join the final lists and the staged items are cleared, so loading further files adds to what is already available.

Why, and what it keeps

Problems stay visible and the question is asked only when it matters.

kept 7. Start working with the new definitions.

The system presents the category tree with nothing selected, the empty state in the information pane, and previous search results forgotten.

takes the place of today's 1, 2

Why, and what it keeps

The person lands on a clean, predictable view.

  • A category's icon is chosen in this order: orphaned, then empty, then normal.
  • A category is visible when empty categories are switched on. Otherwise it is visible only if it has at least one visible policy or one visible subcategory.
  • A category appears in the tree only when it passes the visibility rule; each shown category gets an icon by its kind and carries its visible subcategories below it, and the tree is sorted.
  • A policy's icon is chosen in this order: preference, then plain when it has no configurable elements, then "extra configuration" when it has some.
  • After the category tree is rebuilt from the loaded definitions, no category, policy or highlighted item is selected and the information pane shows the empty state.
  • When nothing is selected, the title and support lines are hidden and the pane reads "Select an item to see its description.".
  • The category tree selection follows the category shown in the right pane.
  • The right pane lists the chosen category in this order: an "Up: <parent name>" row marked "Parent" when the category has a parent, then visible subcategories by name, then visible policies by name. Each policy row shows its state and its comment text.
  • For a selected or highlighted category the pane shows its title, "This category contains N policies and M subcategories." ("The selected category" when highlighted but not opened) and its explanation. The counts include every policy and subcategory, hidden or not.
  • For a selected policy the information pane shows its title, "(no requirements information)" when it has no support rule or "Requirements:" plus the support name, and its explanation. A notice that the policy is a preference appears only for preferences.
  • When the list is rebuilt, the policy already selected is selected again and revealed only if it is still listed, that is, it sits in the category shown and passes the visibility rule; otherwise nothing is selected. Then, if the policy is in the same category and the list still has that many rows, the earlier top row is put back, so the policy is not guaranteed to stay in view.
  • Clearing the search forgets the results, so reopening them reports that no search has been run.

kept 8. See each policy's setting and comment as before.

The system works out each policy's state and comment in each area from the stored settings and the live ones, and applies the filters.

takes the place of today's 1, 2

Why, and what it keeps

The rules of states and filters stay exactly as they are, with no change for the person.

  • For a policy's list elements, a marked-for-deletion list counts as one deleted element, and a list that holds any values counts as a present element and cancels that deletion.
  • A policy's lists of on-values and off-values count as enabled or disabled evidence for each value in them that is present, using the list's own key when it names one.
  • A policy is visible only if it applies to a chosen area (user, computer or both). With "Only Filtered Policies" on, it must also pass the filter for a chosen area it applies to; passing for either one is enough.
  • With both areas shown, a policy that applies to both areas shows its common state followed by "(2)" when both match, the computer state followed by "(C)" when only the user is Not Configured, the user state followed by "(U)" when only the computer is Not Configured, and "Mixed" otherwise.
  • A filter on state keeps only policies whose state in the checked area is Configured (Enabled or Disabled), Not Configured, Disabled or Enabled, as chosen.
  • A value in a policy file counts as marked for deletion when a deletion marker names it, when the key has a clear-all marker, or when a delete-values list for the key names it, regardless of case. Entries are examined in sorted order, and a value whose name sorts after the marker is stored as present and cancels the deletion, whenever it was written and whichever marker kind came before.
  • Listing the values of a key in a policy file leaves out the marker entries unless the caller asks for them.
  • For any other element (number, text, choice, multi-line text), a value marked for deletion counts as a deleted element and a value that is present counts as a present element.
  • The live registry never reports a value as marked for deletion.
  • A policy with a registry value of its own counts as enabled evidence when that value holds its 'on' value, which is the number 1 when the template gives none, and as disabled evidence when it holds its 'off' value or is marked for deletion when the template gives none.
  • Reading a value from a policy file gives nothing when the value is absent or marked for deletion.
  • A value in the live registry counts as present when its key exists and, unless the value name is empty, the key lists a value of that name, regardless of case. An empty name means the key itself.
  • If any element is present, the elements add their count to the enabled evidence; only when none is present do deleted elements add to the disabled evidence.
  • A support definition met a second time anywhere in one evaluation counts as not met, because the list of definitions seen is never emptied. Two entries that point at the same definition, with no cycle, make the second one not met.
  • With both areas shown, the comment column is empty when neither area has a comment, shows "(multiple)" when both have one, and otherwise shows the single comment.
  • A policy's comment in one area is empty when that source has no comment file or holds no comment for the policy, and otherwise the saved text.
  • A value in a policy file counts as present only if it is stored and not marked for deletion.
  • A policy's state in one area reads "Enabled", "Disabled", "Not Configured" or "Unknown"; the computer source is read for the computer area and the user source for any other.
  • When the caller asks for 'any' matching, a support definition whose logic is all-of needs every entry met, and any other definition needs one entry met. When the caller does not ask for 'any', every definition, all-of included, is met by one entry. A definition with no entries, or none met, is met only when all are required. Plain product entries are checked before nested definitions.
  • A support entry for a product that has versions beneath it, whether a version range or a plain entry for a parent product that is not itself chosen, counts as met when any version in its range, or a sub-product directly beneath one, is chosen. The range runs from the entry's minimum (0 if none) to its maximum (the highest version if none). A range entry never matches on its own product, and a product with no versions beneath it never matches this way.
  • A value counts as present when: for a deletion marker, it is marked for deletion; for a number, it exists as a whole number and equals the expected number; for text, it exists as text and equals the expected text. A value of the wrong kind is not present.
  • A filter on managed policies hides preferences when managed policies are wanted, and hides managed policies when preferences are wanted.
  • A REG file cannot be used as a source for checking whether a value will be deleted: the request fails with 'not implemented'. Applying a newer policy file over an older one to a REG file fails this way for any dropped value under a policy branch.
  • A policy passes the filter only when it passes every active part of it.
  • Text read from a policy file stops at its first empty character, and a multiple-string value ends at its first empty string.
  • For a checkbox element: a value marked for deletion counts as one deleted element. Otherwise, each present off value (or off-list value) counts a tenth of a deleted element, and each present on value (or on-list value) counts one present element. A checkbox whose template declares no on value or on list adds no present evidence, even if it holds 1.
  • A filter on comments keeps only policies that have a non-empty comment in the checked area, or only those that have none, as chosen.
  • When a policy lists no supported-on information, it counts as supported only if the caller allows unlisted policies. The same applies to a support entry that names no known product.
  • A REG file cannot be used as a source for reading a value: the request fails with 'not implemented'. Applying a newer policy file over an older one to a REG file fails this way for any dropped value under a policy branch.
  • With both areas shown, a policy that applies to one area shows that area's state followed by "(C)" for computer or "(U)" for user. With a single area shown, only that area's state is shown, without a suffix.
  • A stored policy file value is read back as text for text and expandable text, a 32-bit or 64-bit number for numbers, a list of strings for multiple strings, and raw bytes for every other type.
  • A policy is Enabled when enabled evidence exceeds disabled evidence, Disabled when disabled exceeds enabled, Not configured when there is no evidence either way, and Unclear when both are equal and above zero.
  • A REG file cannot be used as a source for listing a key's values: the request fails with 'not implemented'. Applying a newer policy file over an older one to a REG file fails this way for any dropped value under a policy branch.
  • Reading a value from the live registry gives nothing when the key is missing. Signed numbers are returned as the unsigned numbers policies use, and environment variables in text are not expanded.
  • A filter on products keeps only policies supported by the chosen products, honouring the options to match any product and to include policies with blank support.
  • A REG file cannot be used as a source for asking whether a value is present: the request fails with 'not implemented'. Applying a newer policy file over an older one to a REG file fails this way for any dropped value under a policy branch.
  • A support entry for a product counts as met in two cases. The entry is not a version range and that exact product is among the chosen products. Or the product has versions beneath it, and any of those versions or their sub-products is chosen, even when the product itself is not.

  • A REG file cannot be used as a source for asking whether a value is present: the request fails with 'not implemented'. Applying a newer policy file over an older one to a REG file fails this way for any dropped value under a policy branch.
  • A support entry for a product counts as met in two cases. The entry is not a version range and that exact product is among the chosen products. Or the product has versions beneath it, and any of those versions or their sub-products is chosen, even when the product itself is not.
