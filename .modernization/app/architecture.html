                Risks the proposal accepts6
                • The target stack names no operating system, but the registry, loaded user hives, Group Policy refresh, the Windows installer tool, ownership of folders and the directory account lookup exist only on Windows, so the design is a Windows design and every part that reaches them must run on a Windows machine. Bun on any other system cannot provide them.
                • Placement: the application, the installer work and every machine adapter run in one process on the person's own Windows machine; the preference store (PostgreSQL) runs on that machine too, so each installation brings its own database to install and migrate. Placement: the outside systems tie the design to these platforms. The registry keys and loaded user hives, the directory (Active Directory), the template and comment folders and the machine's policy-definitions folder belong to the machine the policy is for, so they work only for the machine the part runs on: a person using a remote server would edit the server's policy, not their own. The Microsoft download site needs outbound access on any host. The build's version file is a build-time file and is host-neutral.
                • The installer is not a separate part here, only a module of the application, and it has a stated trigger and host: it is started only when the person asks to get definitions (or accepts the offer), never on a schedule, and it runs on the same Windows machine as the policy folders, in an administrator session, because it takes ownership of folders, runs the Windows installer tool and writes to the machine's policy-definitions folder.
                • Decision for the new stack: the rule keeps downloads to TLS 1.0 to 1.2. Bun does not offer 1.0 or 1.1 by default and 1.0 and 1.1 are retired, so the target proposes a floor of 1.2 and also accepts 1.3, a departure from the rule that the product owner must confirm.
                • Module boundaries are held by convention, so a careless import can quietly couple two domains. The whole application ships and scales as one, including the rarely used installer.
                • Alongside, the preference store holds the Workspace's remembered choices in PostgreSQL through Drizzle, replacing the old settings key; where the old key was unavailable the program carried on silently with defaults, so the store being down must degrade the same way.

                Cost of the choice: Simplest to build, run and test and the only cut where the machine's registry and folders are in the same process as the rules, at the price of discipline to keep domains apart and of a database per installation.

                Alternatives considered2
                Screens apart from services, one storage domain6 domains

                The screens hold only the session; the rules run in separate services over a typed contract. Raw editing and viewing share one storage domain, so one service guards every write. The installer runs as its own job.

                Cost: Clean separation of what people see from what is decided and one guarded place for all writes, in exchange for more moving parts, a contract to maintain, and merging view and raw editing into one domain that is larger.

                • The installer job has a stated trigger and host: it is started only when the person asks to get definitions (or accepts the offer), never on a schedule, and it runs on the same Windows machine as the policy folders, in an administrator session, because it takes ownership of folders, runs the Windows installer tool and writes to the machine's policy-definitions folder.

                Shared engine for definitions and settings, source services apart5 domains

                The pure decisions about definitions and settings live in one shared library used by the screens; only the services that reach the machine's stored policy are apart. Getting definitions belongs to the session, so it runs inside the screens' own process on the machine.

                Cost: Rules that need no outside system run anywhere and are cheap to test, with fewer domains to cross, at the cost of a library every part depends on, a larger session domain, and an elevated screens process during installation.
