Decisions (37)

Outside systems (8)

Computer file system folders · Chose: Carried by apps/api: the Bun service runs on the person's own Windows machine and reads, writes and lists folders (POL files, template folders, export targets) directly with Bun and node:fs; the web app asks it through the HttpApi contract and never touches disk.
Trade-off: Chose the local API over browser file pickers because the program must edit real policy files at fixed Windows paths and a browser sandbox cannot; assumes the service and the browser both run on the same machine as the files.
Governs: API service
Windows registry policy keys and loaded user hives · Chose: Carried by apps/api: reads and writes policy keys, and loads and unloads user hives, by running reg.exe and PowerShell from Bun on the person's machine, behind one registry port that the domain layer sees only as plain data.
Trade-off: Chose spawning the built-in Windows tools over a native Node addon because it needs no compiled dependency and works on Home editions; assumes the service runs elevated when writing machine policy and that the machine is Windows.
Governs: API service
Administrative template files (ADMX and ADML) · Chose: Carried by apps/api: reads ADMX and ADML files from the chosen folders through the file system carrier and hands their text to the pure parsers in packages/domain; schemas for the parsed result live in packages/contracts.
Trade-off: Chose parsing in the domain over parsing in the API handler so the rules stay pure and testable with fixture text; the API owns only reading bytes.
Governs: API service
Windows registry settings key of Policy Plus · Chose: Replaced by the Preference store: remembered choices (language, definitions folder, offers considered) are rows in PostgreSQL through Drizzle in packages/database, reached by apps/api; the old registry key is not read or written.
Trade-off: Chose the database that the confirmed architecture already includes over keeping a registry key because the Workspace domain is held by the Preference store container; the trade-off is that existing registry settings are not migrated, which is assumed acceptable (a one-time import can be a story if the owner wants it).
Governs: Database
Generated version source file · Chose: Replaced: the Git version is stamped at build time by a script in packages/tooling that writes it into an environment value the API reports, instead of generating and compiling a version source file.
Trade-off: Chose a build-time environment value over a generated source file because the TypeScript and Bun build has no compile step that needs one and a committed generated file goes stale.
Governs: Tooling
Policy comment files (CMTX) · Chose: Carried by apps/api: reads and writes CMTX files beside the policy sources through the file system carrier, with the XML encoding and decoding in packages/domain.
Trade-off: Chose keeping CMTX files on disk over storing comments in the database because Windows and other tools read these files in place; the API owns only the bytes.
Governs: API service
Active Directory domain · Chose: Carried by apps/api: resolves user and group accounts and their profile and policy-object locations by calling the machine's own Windows directory tools (PowerShell and ADSI) from Bun, on the person's machine, and returns a plain result or an unavailable status when no domain is reachable.
Trade-off: Chose the local machine's directory access over a hosted lookup service because only the person's machine is joined to the domain with their credentials; assumes a domain may be absent, so the contract models unavailable as a normal outcome.
Governs: API service
Microsoft download site · Chose: Carried by apps/api: downloads the policy template package with Bun fetch from the Microsoft download site, extracts it into the chosen folder through the file system carrier, and reports progress and failure through the contract; the web app never calls the site itself.
Trade-off: Chose server-side download over a browser download because the package must be unpacked into a Windows folder and the browser cannot write there; assumes internet access is optional and failure is a normal outcome.
Governs: API service

Conventions of each layer (25)

Contracts · Chose: Every request, response and error is an Effect Schema; define it once here and generate the OpenAPI document from the HttpApi, never write the document by hand.
Trade-off: Chose one source for types and the document over separate hand-kept specs because they cannot disagree.
Contracts · Chose: An outside system being absent or failing (no domain, no network, no admin rights) is a tagged result in the schema, not a thrown error or an HTTP 500.
Trade-off: Chose modelled outcomes over exceptions because the analysis treats these as normal outcomes the screen must show.
Contracts · Chose: Do not import from any other workspace package; contracts depend only on effect.
Trade-off: Keeps the layer reachable by all without cycles.
Domain · Chose: No I/O, clock, randomness or environment access: functions take data in and return data or Effect values of data; outside systems arrive as ports declared here and implemented in apps/api.
Trade-off: Chose ports over direct imports so every rule is testable with fixture text.
Domain · Chose: One folder per capability, named as in the plan; shared helpers go in a folder named for what they do, never utils or common.
Trade-off: Capability folders keep the plan-to-code trace direct.
Domain · Chose: Parse ADMX, ADML, CMTX, POL and REG text into schema-checked values at the edge; downstream rules never see raw XML or bytes.
Trade-off: One parse boundary stops malformed input spreading.
Database · Chose: Change the schema only through a Drizzle Kit migration that is committed; never edit a generated migration after it is merged.
Trade-off: Merged migrations are history other databases already ran.
Database · Chose: Queries are Effect SQL functions returning contract types' data shapes; callers never receive Drizzle table objects.
Trade-off: Keeps persistence replaceable behind the layer.
Database · Chose: Tests run against a real PostgreSQL with migrations applied from empty; no mocked client.
Trade-off: Mocks hide SQL and migration faults.
API service · Chose: Handlers are thin: decode with the contract, call domain functions and carriers, encode; rules never live in a handler.
Trade-off: Keeps rules in the tested pure layer.
API service · Chose: Each outside system (file system, registry, directory, download) is one Effect Layer implementing a domain port; the Windows ones have an in-memory fake used in tests and non-Windows runs.
Trade-off: Fakes let tests run anywhere while Windows tools stay isolated.
API service · Chose: Spawn reg.exe and PowerShell with an argument array, never a built shell string, and validate key paths and account names against the contract schema first.
Trade-off: Prevents command injection from user-typed registry keys and names.
API service · Chose: Writes to a policy file go to a temporary file and are renamed over the target so a failed save never leaves a half-written file.
Trade-off: A corrupted policy file is worse than a failed save.
UI components · Chose: Components take data and callbacks only, never call the API or router; each has a Storybook story covering its states, with an axe check.
Trade-off: Keeps components reusable and accessibility proven in isolation.
UI components · Chose: Use Tailwind 4 design tokens and the shadcn on Base UI primitives; do not add colors, spacing or icon sets outside them.
Trade-off: One visual language across screens.
Web app · Chose: Fetch through TanStack Query using a client generated from the contract; no hand-written fetch calls or duplicated response types.
Trade-off: The contract stays the one source of types.
Web app · Chose: Every visible string is a Paraglide message; no literals in components, and policy text from definitions is shown as data, not translated.
Trade-off: The product's own language setting must switch all chrome.
Web app · Chose: Forms use TanStack Form with the contract schema as the validator, so client and server reject the same input.
Trade-off: Avoids drift between client and server validation.
Web app · Chose: Server rendering must not touch the machine: only the API reads disk or registry, and route loaders call it over HTTP.
Trade-off: Keeps the web app unprivileged.
End-to-end tests · Chose: Write each test from the story's acceptance criteria and commit it before the code; it fails first, and runs against the real api with fake Windows carriers.
Trade-off: Tests-first proves the test can fail and keeps a deterministic Windows-free run.
End-to-end tests · Chose: Every page visited is scanned with axe, and a violation fails the test.
Trade-off: Accessibility is a gate, not a review item.
End-to-end tests · Chose: Select elements by role and accessible name, never by CSS class or test id unless no role exists.
Trade-off: Role queries double as an accessibility check.
Tooling · Chose: Layers extend the shared configs here and add no local lint or format rules; a rule change is made here once.
Trade-off: One policy for every layer.
Tooling · Chose: Commits follow conventional commits and lefthook runs lint, format and the affected layers' checks before commit; skipping hooks is not allowed.
Trade-off: Early failure beats CI failure.
Tooling · Chose: knip must pass with no unused files, exports or dependencies in any layer.
Trade-off: Keeps dead code out of an incremental port.

Technical areas (4)

libraries · Chose: Only the stack's libraries, plus fast-xml-parser (ADMX, ADML and CMTX XML in packages/domain), a small zip reader (fflate) in apps/api for the Microsoft template package, and Effect's own Schema, HttpApi, SQL and Layer modules for every service seam; no state library beyond TanStack Query and Form.
Trade-off: Chose fast-xml-parser and fflate over hand-written parsers or shelling to a zip tool because they are pure TypeScript, run on Bun with no native build and keep the domain free of I/O; chose Effect modules over adding a second DI or validation library because the stack already commits to Effect. Assumes the template package is a standard zip and the XML is well-formed enough for a tolerant parser with schema checks after.
Governs: Workspace
tooling and environment · Chose: Bun runs scripts and the API, Turborepo orchestrates one task name per layer (lint, typecheck, test, build) cached by inputs, TypeScript is strict with project references, configuration comes from typed environment values read once through Effect Config, and the app targets Windows 10 and 11 only, run locally as api plus web.
Trade-off: Chose Turborepo task names that every layer implements over per-layer ad hoc scripts so one command verifies any layer and CI stays uniform; chose Effect Config over reading process.env freely so missing values fail at start. Assumes developers can build on any OS but the registry and directory carriers only function on Windows, so those carriers sit behind ports with in-memory fakes elsewhere.
Governs: Workspace
testing · Chose: Vitest for domain, contracts, database and api with fixture text for ADMX, ADML, POL and REG files; database tests run against a real PostgreSQL started by the test task, never a mock; Windows-only carriers are tested against fakes behind their ports plus a few Windows-gated tests; e2e is Playwright with axe against the running product, written before the code it tests; every rule and story carries its legacy rule as a test name.
Trade-off: Chose a real PostgreSQL over mocked queries because mocks hide migration and SQL faults, and chose port fakes over mocking reg.exe or PowerShell calls so domain and handler tests run anywhere; the trade-off is slower database tests and a Windows-gated subset. Assumes a Postgres instance is available locally or in CI via a container.
Governs: Workspace
knowledge in code · Chose: Behaviour lives in code and tests, not prose: contract schemas carry doc annotations that feed the OpenAPI document, each domain folder has a short README-free index with typed exports, rule names in test titles cite the legacy rule, and AGENTS.md holds only what code and tools do not show; decisions with trade-offs are kept in the plan, not copied into source.
Trade-off: Chose schema annotations and test names as the home of knowledge over separate design documents because they are checked and cannot drift silently; the trade-off is that rationale beyond a line is found in the plan, not beside the code. Assumes agents and developers read AGENTS.md before editing a layer.
Governs: Workspace

Contracts
# Contracts: the Effect Schema types and the HttpApi contract the OpenAPI document is generated from

Stack: language and runtime: TypeScript on Bun, in a Turborepo workspace of packages and apps; services: Effect 4 HttpApi with Effect Schema, with an OpenAPI document generated from the same contract, served on Bun.

- Every request, response and error is an Effect Schema; define it once here and generate the OpenAPI document from the HttpApi, never write the document by hand.
- An outside system being absent or failing (no domain, no network, no admin rights) is a tagged result in the schema, not a thrown error or an HTTP 500.
- Do not import from any other workspace package; contracts depend only on effect.
