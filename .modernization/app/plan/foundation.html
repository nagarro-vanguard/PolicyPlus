Decisions (36)

What carries over (8)

Building and versioning Policy Plus · Chose: carry as a build step in layer-tooling that injects the Git version into the API and screens (see decision-5).
Trade-off: Chose carry over drop because decision-5 already replaces the generated version file with a build step, and the capability is a single action: stamping the Git version at build; the inputs do not say whether to keep it, so carrying it is the recommended answer. Assumes builds run in a Git checkout or CI supplies the version.
Governs: Tooling
Getting Microsoft policy definitions · Chose: carry: the service downloads, unpacks and stores Microsoft's template package (see decision-8), parsed by layer-domain and stored by layer-data.
Trade-off: Chose carry over upload-only because the analysis lists this capability (download and unpack Microsoft's package, 6 actions) and decision-8 already carries it in layer-api; users can still upload ADMX and ADML packages (decisions 1 and 3), so dropping it would remove only the one-step fetch from Microsoft, not the way to load definitions. The inputs do not settle drop versus carry, so carrying is the recommended answer. Assumes outbound HTTPS to Microsoft is allowed.
Governs: Services
Using the product · Chose: carry as a settings row in PostgreSQL exposed through the API and shown on a settings screen (see decision-4).
Trade-off: Chose to carry it over dropping it because the policy text language drives how templates are loaded and displayed; assumes one shared row, as no sign-in exists in the inputs.
Governs: Data
Choosing and saving policy sources · Chose: carry with its sources replaced: POL file by upload and download, registry, user hive and Group Policy object sources by REG or POL import and export, and the live system source dropped (see decision-1, 2 and 7).
Trade-off: Chose to carry the capability with file-based sources over dropping it because choosing and saving policy state is the core flow; the live registry and Active Directory sources cannot run on a server, and the owner is assumed to accept that loss.
Governs: Domain
Changing policy settings · Chose: carry in full: Enabled, Disabled, Not configured with options and comment, and SPOL text in and out, with rules in layer-domain and state stored by layer-data.
Trade-off: Chose to carry it unchanged in behaviour over redesigning it because it is the product's purpose and its rules are pure and testable in Domain; assumes the rules transfer as analysed.
Governs: Domain
Finding policies · Chose: carry in full: filters and search by ID, text and registry key and value, with the matching rules in layer-domain and results shown by layer-web.
Trade-off: Chose to carry it over dropping or deferring it because administrators locate policies mainly by search; chose Domain-side matching over database queries to keep the rules identical and testable, assuming template data fits in memory per request.
Governs: Domain
Editing policy files directly · Chose: carry: raw key and value editing of an uploaded policy file, with REG import and export, rules in layer-domain.
Trade-off: Chose carry over drop because the analysis lists this capability (35 actions: change the raw keys and values of a policy file, REG in and out) and no input names a replacement for those actions; the inputs do not settle drop versus carry, so carrying is the recommended answer. Assumes REG round-trip fidelity is tested and that raw editing acts on the uploaded policy file stored by layer-data.
Governs: Domain
Browsing policy definitions · Chose: carry in full: categories, products, support rules, template files and policies with detail views, built on parsed definitions from layer-domain.
Trade-off: Chose to carry it over deferring it because every other capability selects policies from these views; it is the largest capability, so it is expected to split into several stories.
Governs: Screens

Outside systems (8)

Computer file system folders · Chose: Replace direct folder access with browser upload and download through the API: the service accepts files (POL, ADMX, ADML, CMTX, REG, SPOL) as request bodies and returns saved files as downloads. The service reads no user folder; stored files live in the Data layer.
Trade-off: Chose upload and download through layer-api over server-side disk access because a server rendered web product cannot see the user's folders and server disk access would leak across users. Assumes users work from files on their own machine and accept a save-as-download step.
Governs: Services
Windows registry policy keys and loaded user hives · Chose: Replace live registry reads and writes with a registry policy source modelled in the Domain layer and filled from imported REG files and POL files. Reading or writing the live machine registry and loaded hives is not carried; the sources that need it become import and export of files.
Trade-off: Chose file based import and export over a live registry bridge because an Effect service on Bun in a server cannot reach the end user's Windows registry, and a local agent would add a second product to ship and secure. Assumes the product owner accepts losing live system editing in favour of file round trips.
Governs: Domain
Administrative template files (ADMX and ADML) · Chose: Carry in layer-domain as pure parsers from file text to typed policy definitions, with the uploaded or downloaded template packages stored by layer-data as rows and loaded per language.
Trade-off: Chose pure parsing in Domain with storage in Data over parsing inside the API handlers because the rules stay testable without I/O and one parser serves upload and the Microsoft download. Assumes template packages are small enough to store as text in PostgreSQL.
Governs: Domain
Windows registry settings key of Policy Plus · Chose: Replace the registry settings key with a settings table in PostgreSQL, read and written through a Data repository and exposed by the API.
Trade-off: Chose a database table over browser local storage or a settings file because the setting is then read and written through the same API and Data repository as other state, and is covered by migrations and tests. Assumes no sign-in exists in the inputs, so the settings are one shared row for all users; per-user settings, and settings that follow a user across devices, would need a later story that adds sign-in.
Governs: Data
Generated version source file · Chose: Replace the generated source file with a build step in layer-tooling that reads the Git version and passes it to the API and screens as a build-time environment value; no generated file is committed.
Trade-off: Chose an environment value injected at build over a generated, checked-in source file because it avoids stale or dirty files in the repository and works the same under Turborepo caching if the value is a declared input. Assumes builds run in a Git checkout or receive the version from CI.
Governs: Tooling
Policy comment files (CMTX) · Chose: Carry in layer-domain as a pure parser and writer for CMTX text; comments are stored by layer-data next to the policy state they belong to and exported as CMTX files on download.
Trade-off: Chose storing comments as data with CMTX as an import and export format over keeping CMTX files as the system of record because comments then stay consistent with the policy state they belong to and are covered by migrations and tests. Assumes round-trip fidelity of the CMTX text is tested; no comment search is carried, since the analysis shows none.
Governs: Domain
Active Directory domain · Chose: Replace the live Active Directory lookup of a user's Group Policy object with importing that object's POL file by upload; the service makes no directory connection.
Trade-off: Chose upload of the GPO's registry.pol over an LDAP or SMB connection from the server because a hosted service typically is not on the domain and holding domain credentials is a security cost out of proportion to this need. Assumes administrators can copy the file from SYSVOL; a directory connector can be a later story.
Governs: Services
Microsoft download site · Chose: Carry in layer-api: the service downloads Microsoft's policy template package with the Effect HttpClient from a configured URL, unpacks it in memory, hands the files to Domain for parsing and has Data store them.
Trade-off: Chose a server side download with a configurable URL over a client side download because the server can validate, unpack and cache the package once for all users. Assumes outbound HTTPS to Microsoft is allowed from the service and the package format stays an archive of ADMX and ADML files.
Governs: Services

Conventions of each layer (16)

Workspace · Chose: Commit with conventional commits; lefthook runs lint, format and typecheck on staged files before commit, and commitlint on the message.
Trade-off: Chose hooks over CI-only enforcement because feedback arrives before review; CI repeats the same checks so hooks can be skipped without harm.
Workspace · Chose: Run work through Turborepo (bun run check at the root); a layer imports only layers beneath it, and knip fails on unused exports or dependencies.
Trade-off: Chose enforced dependency direction over convention alone because layers stay replaceable; assumes knip config lists the entry points of each layer.
Domain · Chose: Pure code only: no file, network, database or clock access; take inputs as arguments and return typed results or Effect errors.
Trade-off: Chose purity over convenient I/O inside rules because it keeps rules testable without setup.
Domain · Chose: Model failure as typed Effect errors (for example malformed ADMX), never thrown exceptions or null; an unknown policy element is kept and reported, not silently dropped.
Trade-off: Chose typed errors over exceptions so callers must handle each case; keeping unknowns preserves round-trip fidelity of policy files.
Domain · Chose: Policy values and POL, REG and CMTX text round-trip byte-faithfully where the legacy format allows; a round-trip test accompanies every parser and writer.
Trade-off: Chose round-trip tests over spot checks because users overwrite real policy files with the output.
Contracts · Chose: Every request and response is an Effect Schema; the HttpApi group per capability is the only source of the OpenAPI document, regenerated by a script and checked for drift in CI.
Trade-off: Chose generation over hand editing so Screens and API cannot disagree.
Contracts · Chose: File content crosses the API as upload bodies and downloads with an explicit media type and size limit; the contract names the limit.
Trade-off: Chose explicit limits over defaults because policy files are untrusted input.
Data · Chose: Schema changes only through Drizzle Kit migrations committed with the change; a migration is never edited after it merges.
Trade-off: Chose forward-only migrations over editing history so every environment reaches the same schema.
Data · Chose: Repositories return Domain types, not Drizzle rows, and run inside Effect SQL transactions when more than one table changes.
Trade-off: Chose mapping at the boundary over leaking rows so the schema can change without touching Domain.
Services · Chose: Handlers only decode, call Domain and Data, and encode; no policy rule lives in a handler. Operational configuration (download URL, size limits, database address) comes from validated environment configuration; the product's own settings, such as the policy text language, are read through the Data repository (decision-4), not from configuration.
Trade-off: Chose thin handlers over logic in handlers because rules stay testable in Domain. Chose to keep operator-set configuration apart from user settings because decision-4 stores the product's settings in a database table, so only deployment values belong in environment variables.
Services · Chose: Uploaded files are validated for size and type before parsing, and the Microsoft download accepts only the configured HTTPS host.
Trade-off: Chose allow-listing over open fetching to limit server-side request risk; assumes the URL is operator-set.
Components · Chose: Components are presentational, styled with Tailwind tokens, built on Base UI for behaviour and accessibility, each with a Storybook story; no data fetching or routing.
Trade-off: Chose Base UI primitives over custom widgets so keyboard and screen reader behaviour comes for free.
Screens · Chose: Server data goes through TanStack Query and route loaders; forms use TanStack Form with Effect Schema validation; every visible string is a Paraglide message.
Trade-off: Chose messages from the start over retrofitting because every visible string would otherwise have to be found and replaced later; this is independent of the policy text language, which only chooses the template language loaded (decision-3), not the language of the screens' own text.
Screens · Chose: Screens call the API through a client generated from the contract and never import Data or Domain parsers.
Trade-off: Chose the generated client over direct imports to keep the layer boundary and the contract authoritative.
Black-box tests · Chose: Tests drive only screens and the public API against a seeded database, assert accessibility with axe on each screen, and never reach into code of other layers.
Trade-off: Chose black-box isolation over shortcuts so tests prove what a user would see.
Tooling · Chose: Shared configuration is extended by each layer and not copied; changing a rule happens here only.
Trade-off: Chose one source of lint and format rules over per-layer copies to prevent drift.

Technical areas (4)

libraries · Chose: Effect 4 with Effect Schema, HttpApi, HttpClient and Effect SQL for contracts, API, data and the Microsoft download; Drizzle ORM and Drizzle Kit for the schema and migrations; fast-xml-parser for ADMX, ADML and CMTX text; fflate for unpacking the Microsoft archive in memory; TanStack Query and Form in Screens; Zod is not used. No library outside the stack is added without a story that needs it.
Trade-off: Chose one schema library (Effect Schema) for contract, validation and OpenAPI over adding Zod because a second schema language would duplicate every type. Chose fast-xml-parser and fflate (small, pure JS, run on Bun) over Node-only native modules because Domain must stay free of I/O. Assumes the template archive format stays zip-compatible and files are small.
Governs: Workspace
tooling and environment · Chose: Bun is the package manager and runtime, pinned by a version file; Turborepo runs one task per layer (lint, typecheck, test, build) with declared inputs; local PostgreSQL runs from a Docker Compose file at the root; configuration is read from environment variables validated by Effect Schema at start-up, with an .env.example listing each; the Git version is a declared Turborepo input.
Trade-off: Chose Docker Compose for the local database over requiring a locally installed PostgreSQL because every developer and the black-box tests get the same version. Chose validated environment variables over config files because the service and screens share one place that fails fast. Assumes Docker is available to developers and CI.
Governs: Tooling
testing · Chose: Vitest per layer: Domain with example-based unit tests, table-driven over sample ADMX, ADML, POL, REG, CMTX and SPOL files, plus a round-trip test per parser and writer; Data against a real PostgreSQL test database, no mocks; API through the HttpApi test client; Components with Storybook stories and Screens with Vitest tests of their pure logic. Playwright with axe in layer-e2e drives the running product, one accessibility check per screen. A story is done when its layer checks and its black-box test pass.
Trade-off: Chose a real PostgreSQL in Data tests over in-memory fakes because migrations and SQL behaviour are what can break. Chose black-box Playwright for end-to-end rules over component-only tests because the legacy behaviour is user-visible, and chose table-driven Vitest tests over adding Testing Library or a property-testing library because neither is in the stack and decision-9 allows no library outside it without a story. Assumes CI can run Docker and Playwright browsers; no coverage threshold is set because the inputs give none.
Governs: Workspace
knowledge in code · Chose: The legacy rules live as code and tests, not documents: each rule is a named, pure Domain function with a test named after the rule, a short comment naming the legacy source only where the reason is not evident, and domain terms in code match the analysis wording. The Effect Schema types and HttpApi groups are written by hand in Contracts; only the OpenAPI document and the client are generated from them, never hand-written. Decision reasons live in AGENTS.md lines and the story, not in a separate wiki.
Trade-off: Chose rules as tested pure functions with intention-revealing names over a prose rules document because tests cannot go stale silently. Chose comments only for non-obvious legacy quirks over commenting everything to avoid noise. Assumes the analysis vocabulary is stable enough to name code after.

## Rules

- Commit with conventional commits; lefthook runs lint, format and typecheck on staged files before commit, and commitlint on the message.
- Run work through Turborepo (bun run check at the root); a layer imports only layers beneath it, and knip fails on unused exports or dependencies.
Tooling
# Tooling: the shared TypeScript, ESLint, Prettier, knip, markdownlint, commitlint and lefthook configuration every layer extends, on Bun and Turborepo

Stack: language and runtime: TypeScript on Bun, in a Turborepo workspace of packages and apps; checks: Vitest for tests, Playwright with axe for black-box and accessibility tests, ESLint, Prettier, knip, markdownlint, commitlint with conventional commits, lefthook.

- Shared configuration is extended by each layer and not copied; changing a rule happens here only.

## Verify

- `bun run lint && bun run typecheck`
Domain
# Domain: the pure policy rules: reading policy definitions, resolving and editing policy state, with no I/O framework

Stack: language and runtime: TypeScript on Bun, in a Turborepo workspace of packages and apps.

- Pure code only: no file, network, database or clock access; take inputs as arguments and return typed results or Effect errors.
- Model failure as typed Effect errors (for example malformed ADMX), never thrown exceptions or null; an unknown policy element is kept and reported, not silently dropped.
- Policy values and POL, REG and CMTX text round-trip byte-faithfully where the legacy format allows; a round-trip test accompanies every parser and writer.

## Verify

- `bun run typecheck && bun run test`
Contracts
# Contracts: the Effect Schema types and HttpApi contract, and the OpenAPI document generated from it

Stack: services: Effect 4 HttpApi with Effect Schema, with an OpenAPI document generated from the same contract, served on Bun.

- Every request and response is an Effect Schema; the HttpApi group per capability is the only source of the OpenAPI document, regenerated by a script and checked for drift in CI.
- File content crosses the API as upload bodies and downloads with an explicit media type and size limit; the contract names the limit.

## Verify

- `bun run typecheck && bun run test && bun run openapi:check`
Data
# Data: the PostgreSQL schema, Drizzle on Effect SQL repositories and Drizzle Kit migrations

Stack: data: PostgreSQL through Drizzle on Effect SQL, with Drizzle Kit migrations.

- Schema changes only through Drizzle Kit migrations committed with the change; a migration is never edited after it merges.
- Repositories return Domain types, not Drizzle rows, and run inside Effect SQL transactions when more than one table changes.

## Verify

- `bun run typecheck && bun run test && bun run migrations:check`
Services
# Services: the Effect HttpApi service implementing the contract on Bun, and serving the OpenAPI document

Stack: services: Effect 4 HttpApi with Effect Schema, with an OpenAPI document generated from the same contract, served on Bun.

- Handlers only decode, call Domain and Data, and encode; no policy rule lives in a handler. Operational configuration (download URL, size limits, database address) comes from validated environment configuration; the product's own settings, such as the policy text language, are read through the Data repository (decision-4), not from configuration.
- Uploaded files are validated for size and type before parsing, and the Microsoft download accepts only the configured HTTPS host.

## Verify

- `bun run typecheck && bun run test`
