# Stamp every built copy with the version of its code

## Story

As a person using the product, I want when someone runs the build script or the release workflow does, the version is worked out from the code and recorded as a value the Policy Plus API reports, instead of in a generated source file., so that people can tell which code a copy came from without anyone keeping a version file up to date..

## Context

This ports behaviour of the existing product, described in the attachment: 0 rules it must keep and the reading of the code behind them.

Open points, to settle before it is built:
- Should the committed code keep any version value, since the old rule says the committed file holds an empty version but the decision drops the generated file?
- When the code is exactly at a tag, is the version the tag alone, as git reports it?
- Is the build script run automatically with every build, or only when someone or the release workflow runs it?

## Acceptance criteria

**AC-1: The version is the tag, the commit count and.**
Given the code has tags, when the build script runs, then the version is the tag, the commit count and the short commit name that git gives for the current commit.

**AC-2: The version is the short commit name that git.**
Given the code has no tags, when the build script runs, then the version is the short commit name that git gives for the current commit.

**AC-3: The version is worked out from the current commit.**
Given someone runs the build script or the release workflow runs it, when it runs, then the version is worked out from the current commit at that moment.

**AC-4: The version is held as a build-time value rather.**
Given the build script has run, when it finishes, then the version is held as a build-time value rather than written into a generated version source file.

**AC-5: It reports that recorded value.**
Given the version has been recorded, when the API is asked for its version, then it reports that recorded value.

## Terminologies

- Program version: The text git gives for the current commit: a tag, commit count and short commit name when tags exist, a short commit name otherwise; it is not the Windows file version or a release name.
