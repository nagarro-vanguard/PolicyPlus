# Decide whether a policy's support rules are met

## Problem

- People filter policies by the Windows products they run, so a policy must count as supported exactly as the legacy product decided.

## Goal

- Build the shared rules that decide whether the products a policy is supported on are chosen, through support rules, version ranges and nested rules.

## Acceptance criteria

- Given a support entry for a product with versions beneath it, when it is checked, then it is met when any version in its range (minimum 0 if none, maximum the highest if none) or a sub-product directly beneath one is chosen, a range entry never matches its own product, and a product with no versions never matches this way.
- Given a support definition with entries, when it is checked, then with 'any' asked an all-of definition needs every entry met and any other needs one, without 'any' one entry meets every definition, a definition with no or no met entries is met only when all are required, and plain product entries are checked before nested definitions.
- Given a support definition met a second time anywhere in one evaluation, when it is checked, then it counts as not met, so two entries pointing at the same definition make the second one not met.

## Scope

- packages/tooling (the Tooling layer)
- packages/domain (the Domain layer)
- packages/contracts (the Contracts layer)
- packages/data (the Data layer)
- apps/api (the Services layer)
- packages/ui (the Components layer)
- apps/web (the Screens layer)
- apps/e2e (the Black-box tests layer)

## Terminologies

- Support rule: A named group of product entries that says where a policy is supported, with all-of or any-of logic; not a single product.

## Out of scope

- Anything a later story builds on top of this.
