# Refuse invalid template files with clear messages

## Problem

- A broken template must never half-load silently; people need the reason and a choice about continuing.

## Goal

- Build the shared rules that stop loading when a template or language file is invalid and tell the person what went wrong.

## Acceptance criteria

- Given a template declares no target namespace, when the folder is loaded, then loading stops at once, later files are not read, nothing is built and the person sees the error text.
- Given a template file cannot be parsed as XML, when it is loaded, then it is refused with "Couldn't load <path>: The ADMX XML couldn't be parsed: <detail>.", and any other read problem is refused with "The ADMX is invalid: <detail>".
- Given the chosen language file cannot be parsed as XML, when it is loaded, then the template is refused with "The ADML XML couldn't be parsed: <detail>", and any other read problem gives "The ADML is invalid: <detail>".
- Given a language file repeats a text id in its first text table, when it is read, then it is refused as invalid and its template file is not loaded; otherwise each text is kept under its id.
- Given loading definitions reports problems, when loading ends, then the person sees "Errors were encountered while adding administrative templates to the workspace." with each problem and, only where a choice is wanted, is asked "Continue trying to use this workspace?"; with no problems nothing is shown.

## Scope

- packages/tooling (the Tooling layer)
- packages/domain (the Domain layer)
- packages/contracts (the Contracts layer)
- packages/data (the Data layer)
- apps/api (the Services layer)
- packages/ui (the Components layer)
- apps/web (the Screens layer)
- apps/e2e (the Black-box tests layer)

## Terminologies

- Template file: An administrative template (ADMX) that defines categories, products, support rules and policies; not the language file (ADML) that supplies their text.

## Out of scope

- Anything a later story builds on top of this.
