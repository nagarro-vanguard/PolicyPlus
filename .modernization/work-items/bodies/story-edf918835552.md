# Bring in policy settings text and check it as i...: Semantic Text Reader

## Story

As a person using the product, I want a person brings in a semantic policy text, from a file or typed in, and sees at once how many policy settings it holds or the line and reason of the first fault. Nothing is applied in this story., so that administrators find out whether a text is good before they offer it to their computer or user policies, without asking for a separate check, and an earlier text or result never lingers..

## Acceptance criteria

**AC-1: The person sees "Validation successful, N policy settings found.".**
Given text has arrived, when it reads correctly, then the person sees "Validation successful, N policy settings found." and nothing is applied; when it does not, they see "SPOL validation failed: " and the reason.

**AC-2: It is refused with 'Incorrect signature.'.**
Given a text whose first line is not 'Policy Plus Semantic Policy', or whose lines are separated by line feeds alone and so read as one line, when it is read, then it is refused with 'Incorrect signature.'.

**AC-3: The message ends with '(Error found on line N.)'.**
Given any fault in the text, when it is reported, then the message ends with '(Error found on line N.)' naming the line where reading stopped.

**AC-4: The policy is a user policy; any other first.**
Given a policy header line, when it starts with exactly 'U', then the policy is a user policy; any other first word, including 'u' or 'User', makes it a machine policy, and a header with no space after the first word is refused naming only the line.

**AC-5: It is accepted; anything else is refused with 'Unknown.**
Given a policy's state line, when it is 'Not configured', 'Enabled' or 'Disabled' in any letter case, then it is accepted; anything else is refused with 'Unknown policy state.'.

**AC-6: The lines after it are read as the next.**
Given a policy that is Not configured or Disabled, when the text is read, then the lines after it are read as the next policy's header and not as settings; settings are read only under Enabled.

**AC-7: # means a whole number (a non-whole value fails.**
Given a setting value, when it is read, then # means a whole number (a non-whole value fails with a conversion message), a plain non-negative number is an unsigned number, 'True' or 'False' in any case is yes/no, single quotes are text, double quotes are a list of text, 'None' is an empty list, and anything else is refused with 'Unknown option data format.'.

**AC-8: One line is one entry, one text per entry.**
Given a bracketed setting, when it is read, then one line is one entry, one text per entry makes a list, two texts make a table of name and value, and no entries stores the setting with no value; for a list setting the existing entries are then removed unless the definition keeps other entries, and nothing is written, and for any other kind of setting the empty value makes the write fail.

**AC-9: It is recognised in any letter case, a double.**
Given a comment line, when it is read, then it is recognised in any letter case, a double backslash is one backslash and a backslash followed by 'n' is a line break; a comment ending in a lone backslash is refused with 'Escape sequence started at end of comment.', and a backslash followed by any other character with 'Unknown comment escape sequence' naming it.

## Terminologies

- Semantic policy text: A plain text script that states, policy by policy, whether each is Enabled, Disabled or Not configured and its settings; it is not a registry file or a policy file.
- Live check: The reading of the text as soon as it arrives, reporting the count of policy settings or the first fault; it is not the apply step and changes nothing.
