# Map

- **Script:** `S/map-codebase.ts`; one job per set of windows of the code, `map/map-blocks-and-links` and its review; and the Map's two registries, code kinds with their layers and external systems, which grow as the jobs write and are merged once by `registry/propose-entries` (a merging job per registry), reviewed. Every Map job is reviewed.
- **Before the first `next`:** `S/map-codebase.ts prepare` cuts the jobs and picks the lead job, the one holding the most kinds of file and parts, which runs first and alone so the two registries have entries before the rest run in parallel, and prints the jobs and lines; tell the person, and go on. `next` refuses until the jobs are cut. `prepare <job id>` writes that job's own brief (the facts on the parts and technologies its lines touch) and prints its agent's and review's arguments.
- **The order:** the lead job, alone, then every other Map job; a Map job takes an entry from the registries wherever one fits and writes the entry it needs where none does, and each closed batch adds the entries its jobs wrote to the registries the next batch reads. Once every Map job is decided, a merging job per registry that gained entries merges the duplicates (`mergedFrom`). Nothing is written until then: the registries and the map go in one commit. The registries never freeze and never stop the Map.
- **What a job gives back:** every non-blank line of its windows lies in exactly one block, data definition or span (or is an `Unread` line); the review reads every one of those lines and, for each link, sees the call-site line and the target line side by side on its sheet.
- **At done:** `finish` prints the share of blocks reached and how many have no way in, then two lists: names defined in more than one file (every copy is read; a person who does not want a file's copies leaves it out in the request) and names that external links use that a block in scope defines (a link to code in scope names a line inside it). The person reads the counts and decides whether any file is left out or any job is redone; then go on to Capabilities and entities. A refused job's lines are reported as not mapped.
- **Size:** `finish`, `show` and every later stage read the record store a part at a time, so memory does not grow with the code. A `finish` needs free disk of about twice the store's size while it writes (the store is about 4 GB at 50M dense lines).
- **Layers and links added to the Map:** each tier is one layer (the lead job writes the layers the system's tiers need; later jobs write a new one only when none fits), and the merge job merges layers and the code kinds on them together, the check counting a merged layer as the layer that stands for it and refusing two layers of one name. A link of kind `dispatches` is written in the block that can run in place of another, at the lines that show it, and the reach follows it from the target to the block holding it; an interface or abstract member is a block, so a call can reach it. A screen's layout file (a designer file, a layout or markup resource) is one `DataDefinition` named for the screen, each control a field, and its building routine a step of the constructor, never an entry point. `CODE_ANALYSIS_ROOT=<root> bun cli/check-graph.ts --baseline <file>` checks the graph of a finished run.
