# Publish

- **Script:** `S/publish-pages.ts`; the last pass. One job, `publish/brief-the-system`, groups the capabilities into areas, names the screens, chooses the pictures a reader needs, and its review `review/review-agent-findings`; then its `finish` lists the concluding jobs, `topics/write-topic-answers` and its review, over every stage's accepted facts: the entries' topics first, then the risks of each kind, then the system's, whose answer says what the system is for. It writes the areas and every accepted conclusion in one commit once none is to fix or to run.
- **At done:** tell the person what `show` reports. A refused briefing leaves the capabilities in one list; the system's answers are still concluded.
- **Screens and pictures:** the brief lists a `screen` line per place a person's actions start (found by script) and a `menu` line per shape of picture the records can draw (parts, integration, states, data, layers: found by script, each offered only where it has something to show). The briefing writes a `Screen` per screen a person would name, every candidate in exactly one (`kind` `other` for what is no screen: a command, a build step, a test), and a `Figure` per picture a reader needs: the question it answers, the shape from the menu, the records to draw (none draws all) and a caption with no number; a picture the menu lacks is an `other` figure with what is wanted, listed and not drawn. The gate refuses a candidate left out or named twice, a shape the menu lacks, a record its line does not offer, and a caption that states a count. The script draws every box and arrow, writes every count and decides every address; the agent chooses what to show and says what to take from it.
- **Cross-cutting concerns:** the briefing also names and judges the blocks that many capabilities share and that are called from more than one layer (`v_crosscut_candidate`, found by rule; a third of the capabilities, at least two, and callers in two layers). Each candidate is in exactly one `CrossCuttingConcern` with a verdict (`crossCutting`, `sharedDomain`, `neither`); the gate refuses one left out, one named twice and one that is no candidate.
- **Payloads:** `CODE_ANALYSIS_ROOT=<root> bun cli/write-payloads.ts` writes `payloads/system.json` and one typed JSON file per capability (its layers, screens, shared code, data and gaps) from the accepted records and the relation views, checking that each adds up. It also writes `payloads/knowledge.json` (the parts, the technologies and their versions, the answers to each reader's question, the assumptions with how to confirm each, the lives of kinds of data, the links between parts and to outside systems, which capability keeps which kind of data, the briefing's figures, and the risks with the findings they rest on and the places their lines reach, found by script) and the JSON Schema of all three kinds of payload to `payloads/schema/`, from the same Effect schemas. Rendering is `ux-visuals`'.
- **Context:** every place in a payload (the system, an area, a capability, a screen, a layer, an action, a rule) carries a context compiled once in a fixed shape: the ask (left for the reader), the scope, what lies inside, where to look first (own files first, then shared ones, the most widely shared first), the data saved and read, the rules decided there, what is unconfirmed, what was not followed and the commit; capped with a count of what was left out and naming no record id. `write-payloads` checks the shape.
- **ux-visuals:** `CODE_ANALYSIS_ROOT=<root> bun cli/build-ux-visuals.ts`, after `write-payloads`, builds `ux-visuals/` beside the payloads: a page for the system, each area, capability, layer, action and screen, a search, and five figures drawn from the payloads (what the product offers, how the system is layered, what it connects to, how a capability runs, what a screen starts). The pages are an Astro project in `ux-visuals/` of this stage, in the design system of `.agents/shared/page-components`; the payloads are checked against schemas generated from the Effect schemas that wrote them, and every figure is checked (ids named, boxes within budget, no overlap, no arrow through a box) before it is drawn. It needs no stage to run again: it reads only the payloads. Which figure goes where, and how it is drawn, is `diagram-config.ts`; the rules are in `rules/diagrams.md`, and how the pages speak is in `rules/narrative.md`: the pages are addressed by readable names, never by a record id (the build fails on one), and `ux-visuals/language-report.json` lists any word of the analysis's own machinery or boilerplate phrasing in what a reader reads, which makes the run need action. No agent chooses a figure, and no stage records anything about a picture.
- **Bundles:** `CODE_ANALYSIS_ROOT=<root> bun cli/build-bundle.ts screen <address>` or `capability <name>`, after `write-payloads`, writes `<root>/bundles/<kind>-<name>.md`: what the place is, what a person can do there, every rule it applies with where it is decided, the data it keeps, the shared mechanisms it leans on, the risks in its code, what is unconfirmed and what the code cannot tell, then every file it names with the reason and, unless `--no-source`, the whole source of each file; one text to paste into a tool that will modernise it. Nothing is redacted: a secret in the code is in the bundle. A capability's bundle lists its screens, each of which has a bundle of its own to work through in turn.
- **Risks:** an observed risk is a *finding* (a `Fact` with a `risk`); a concluded one is a *risk*, one per distinct weakness over its findings, concluded under the question `risks`. Each risk kind names the stages that see it (`seenAt` in `shared/catalogue/risk-categories.json`): settings, versions, secrets and release steps are found while reading parts and settings; input used unchecked, a check an action skips, data left inconsistent and details sent to a caller are found by the stage that reads every rule a capability's code decides.
