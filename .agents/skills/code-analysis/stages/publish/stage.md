# Publish

- **Script:** `S/publish-pages.ts`; the last pass. One job, `publish/brief-the-system`, groups the capabilities into areas, names the screens, chooses the pictures a reader needs, and its review `review/review-agent-findings`; then its `finish` lists the concluding jobs, `topics/write-topic-answers` and its review, over every stage's accepted facts: the entries' topics first, then the risks of each kind, then the system's, whose answer says what the system is for. It writes the areas and every accepted conclusion in one commit once none is to fix or to run.
- **At done:** tell the person what `show` reports. A refused briefing leaves the capabilities in one list; the system's answers are still concluded.
- **Screens and pictures:** the brief lists a `screen` line per place a person's actions start (found by script) and a `menu` line per family of facts the records can draw (parts, integration, states, data, layers: found by script, each offered only where it has something to show). The briefing writes a `Screen` per screen a person would name, every candidate in exactly one (`kind` `other` for what is no screen: a command, a build step, a test), and a `Figure` per picture a reader needs: the question it answers, the family from the menu, the records to draw (none draws all) and a caption with no number; there may be several of one family. The gate refuses a candidate left out or named twice, a record its line does not offer, and a caption that states a count. The script draws every box and arrow (an arrow is worked out from facts between the boxes, never written), writes every count and decides every address; the agent chooses what to show and says what to take from it.
- **Journeys of today:** `publish/describe-journeys` groups each capability's entry points into the tasks people get done, in the business's words, each entry point and rule in exactly one task, today's steps with intent, system response, certainty and the entry points they come from; one job per capability holding an entry point (`journeys-of-<capability>`), then one (`journeys-merge`) that joins tasks written twice, each reviewed (`checklist-journeys.md`) and gated: every entry point and rule of its brief in exactly one task, each step citing only its task's entry points, no control, medium or name the code uses in an outcome. The jobs are listed from the accepted records (`work/publish/journeys/jobs.json`) and driven by `next` beside the briefing; `write-payloads` writes `payloads/journeys.json` (`{ journeys: Task[] }`, ids `<capability-slug>.<task-slug>`, merges applied) and its JSON Schema, which the target design reads.
- **Cross-cutting concerns:** the briefing also names and judges the blocks that many capabilities share and that are called from more than one layer (`v_crosscut_candidate`, found by rule; a third of the capabilities, at least two, and callers in two layers). Each candidate is in exactly one `CrossCuttingConcern` with a verdict (`crossCutting`, `sharedDomain`, `neither`); the gate refuses one left out, one named twice and one that is no candidate.
- **Payloads:** `CODE_ANALYSIS_ROOT=<root> bun cli/write-payloads.ts` writes `payloads/system.json` and one typed JSON file per capability (its layers, screens, shared code, data and gaps) from the accepted records and the relation views, checking that each adds up. It also writes `payloads/knowledge.json` (the parts, the technologies and their versions, the answers to each reader's question, the assumptions with how to confirm each, the lives of kinds of data, the links between parts and to outside systems, which capability keeps which kind of data, the briefing's figures, and the risks with the findings they rest on and the places their lines reach, found by script) and the JSON Schema of every kind of payload to `payloads/schema/`, from the same Effect schemas. A capability's file is `capability-<slug>.json`, named from its name (as task ids are), so it keeps its name when a stage is run again from nothing; `system.json` names each capability's `file`, and the system's `name`, `repository` and the `commit` Inventory listed (a store made before the commit was kept gets it from `work/inventory/file-summary.json`). Last, `payloads/manifest.json` lists every file written with its digest, the writer's version and the `contractVersion` readers check: `build-app` and `build-bundle` refuse another version and read payloads with no manifest as written before it. Capability files of an earlier run under another name are removed. Rendering is the app's.
- **Context:** every place in a payload (the system, an area, a capability, a screen, a layer, an action, a rule) carries a context compiled once in a fixed shape: the ask (left for the reader), the scope, what lies inside, where to look first (own files first, then shared ones, the most widely shared first), the data saved and read, the rules decided there, what is unconfirmed, what was not followed and the commit (or a plain statement that the source folder is not a git repository, or that the run recorded none); capped with a count of what was left out and naming no record id. `write-payloads` checks the shape.
- **app:** `CODE_ANALYSIS_ROOT=<root> bun cli/build-app.ts [--plan <folder>] [--out <folder>]`, after `write-payloads`, builds `app/` beside the payloads (or into `--out`): a page for the system, each area, capability, layer, action and screen, a search, and the Architecture page of views drawn from the payloads (what the system does, what it is made of, how it is layered, what it reaches, which data it keeps and how that changes; and, when a target exists, the new system's). The pages are the shared Astro app in `.agents/shared/app/` (the same app shows a modernization plan when `--plan` names the folder holding the plan's files), in the design system of `.agents/shared/page-components`; the payloads are checked against schemas generated from the Effect schemas that wrote them. It needs no stage to run again: it reads only the payloads. A view is a list of records of the case the compose step writes to `views.json`, with the principles in `.agents/shared/app/compose/CONTRACT.md`; how the pages speak is in `rules/narrative.md`: the pages are addressed by readable names, never by a record id (the build fails on one), and `app/language-report.json` lists any word of the analysis's own machinery or boilerplate phrasing in what a reader reads, which makes the run need action.
- **Bundles:** `CODE_ANALYSIS_ROOT=<root> bun cli/build-bundle.ts screen <address>` or `capability <name>`, after `write-payloads`, writes `<root>/bundles/<kind>-<name>.md`: what the place is, what a person can do there, every rule it applies with where it is decided, the data it keeps, the shared mechanisms it leans on, the risks in its code, what is unconfirmed and what the code cannot tell, then every file it names with the reason and, unless `--no-source`, the whole source of each file; one text to paste into a tool that will modernise it. Nothing is redacted: a secret in the code is in the bundle. A capability's bundle lists its screens, each of which has a bundle of its own to work through in turn.
- **Risks:** an observed risk is a *finding* (a `Fact` with a `risk`); a concluded one is a *risk*, one per distinct weakness over its findings, concluded under the question `risks`. Each risk kind names the stages that see it (`seenAt` in `shared/catalogue/risk-categories.json`): settings, versions, secrets and release steps are found while reading parts and settings; input used unchecked, a check an action skips, data left inconsistent and details sent to a caller are found by the stage that reads every rule a capability's code decides.
- **Recreating the pictures:** everything the pictures read is in the store or derived from it by script, so they can be made again from the store alone: copy the store's folder, delete its `payloads/`, run `CODE_ANALYSIS_ROOT=<copy> bun cli/write-payloads.ts`, then `bun .agents/shared/app/compose/cli.ts --payloads <copy>/payloads [--target <root>] --out <folder>` twice; the two folders must not differ, and the list of views, with each box and arrow of their text versions, must match what the published payloads give. Two things are not in the store: today's journeys of a run whose Publish ran before they existed (`write-payloads` says so; run Publish again), and the target's records, which are files under `<root>/target/` written by shape-target. A bundle is one place's brief for a builder (its layers, its position, the lives of the data it changes), not the source of any picture.
